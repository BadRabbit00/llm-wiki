# 04 — Хуки для агентов

## Цель

Правила из `AGENTS.md` перестают быть просьбой. Проверка выполняется харнессом,
а не доброй волей модели. То, что можно проверить детерминированно, проверяется стеной.

## Принцип

Хук — это команда, а не текст. Он либо проходит, либо блокирует. Хук **не** редактирует файлы,
**не** вызывает сеть без нужды и **не** печатает ничего, кроме причины отказа.

## Где лежит

Эталонные фрагменты — в репозитории `hooks/` (рядом с `backend` и `wk`), по папке на хук,
внутри `claude/` и `codex/`. Собранные файлы — в `hooks/install/`.

`wk init` раскладывает в проект два файла, версионируются с проектом:

| харнесс | файл в проекте |
|---|---|
| claude-code | `.claude/settings.json` |
| codex | `.codex/hooks.json` |

Личные настройки человека — `.claude/settings.local.json` и `~/.codex/hooks.json`, в git не попадают.

## Контракт харнессов

Совпадает у обоих, и на это опираемся: события `PreToolUse`, `Stop`, `SessionStart`;
структура `{событие: [{matcher, hooks: [{type, command, timeout}]}]}`; JSON на stdin;
код 0 — успех с чтением JSON со stdout, код 2 — блокирующее решение с причиной в stderr,
прочий код — неблокирующая ошибка.

Различается контейнер: у claude-code `hooks` — один из ключей общих настроек,
у codex это отдельный файл с необязательным `description`. Поэтому содержимое групп
одинаково, а файлов два.

Чего в codex нет и на что опираться запрещено: `${CLAUDE_PROJECT_DIR}` и прочие подстановки путей,
типы хуков `http`, `prompt`, `agent`, поля `if`, `once`, `args`, `asyncRewake`.
Все хуки — только `type: "command"` с одной командой `wk`. Это условие переносимости, не стиль.

Источники: `https://code.claude.com/docs/en/hooks`, `https://learn.chatgpt.com/docs/hooks`.

## Передача данных в хук

Все хук-подкоманды `wk` читают JSON события со **stdin**. Аргументов с путями нет.

Причина: подстановки значений payload в аргументы команды не существует ни у одного харнесса —
у claude-code `${...}`-подстановка работает только для хуков типа `mcp_tool`, у codex команда
получает тот же JSON на stdin. Чтение stdin — единственный работающий и единственный переносимый вариант.

Общие поля payload у обоих: `session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`.
Путь правимого файла — `tool_input.file_path`. Неизвестные поля игнорируются: состав payload
у харнессов различается и растёт.

## Состав

### 1. Гейт на остановке — главный

Событие: `Stop`.
Команда: `wk hook check`.

Падает — ход не завершается, агент получает причину как обратную связь и обязан исправить. Это закрывает весь
набор правил, которые сейчас висят просьбами в `AGENTS-snippet.md`: забытый статус,
маркер без факта, факт без маркера, битая ссылка на ID, устаревший блок политик, бюджет строк.

`Stop` у claude-code документирован как блокирующее событие. У codex таблица блокирующих
событий не опубликована, поэтому там тот же `wk check --strict` **обязателен в CI** — не замена, а страховка.

**Почему обёртка, а не `wk check --strict` напрямую.** Блокирует только код 2.
Любой другой ненулевой код — «неблокирующая ошибка»: ход завершается, stderr уходит
человеку, а не модели. `wk check --strict` возвращает 1 при найденных ошибках и 3
при недоступной сети (задачи 06 и 07A), то есть как команда хука не блокирует ничего.
Отображение кодов — часть этого пункта:

| состояние | код `wk check --strict` | код `wk hook check` | почему |
|---|---|---|---|
| проверки прошли | 0 | 0 | завершать ход нечему мешать |
| есть ошибки или предупреждения при `--strict` | 1 | **2** | единственный код, который блокирует |
| сеть недоступна, блок политик не сверен | 3 | 0 + предупреждение в stderr | офлайн — не повод запереть агента в ходе, который он не может завершить |
| нет манифеста `.wiki-project.yaml` | 3 | 0 | в непроектном репозитории хук не мешает |

**`stop_hook_active` обязателен.** В payload события `Stop` claude-code передаёт
`stop_hook_active: true`, если ход уже продолжен по решению предыдущего хука остановки.
`wk hook check` при этом значении возвращает 0 **без проверок**. Без этого условия
неисправимая ошибка даёт бесконечный цикл «блокировка → попытка завершить → блокировка»,
и выйти из него агент не может. Поле отсутствует или не `true` — проверки выполняются.

Текст отказа — одна строка в stderr: что сломано и какой командой починить.
Полный список ошибок агент получает, выполнив `wk check --strict` сам.

### 2. Защита сгенерированного блока

Событие: `PreToolUse`, matcher `Edit|Write|MultiEdit|NotebookEdit`.
Команда: `wk hook guard-block`.
Условие: `tool_input.file_path` перечислен в `policy_blocks` манифеста.
Действие: если правка затрагивает строки между `<!-- wikisvc:begin` и `<!-- wikisvc:end -->` — **код 2**
с текстом: «Блок политик генерируется. Измени правило в вике: `wk propose`, затем `wk policy sync`».

Файл не из `policy_blocks` — код 0, молча.

Matcher `Edit|Write|MultiEdit|NotebookEdit` корректен в обоих, но по разным правилам:
у claude-code это точный список через `|`, у codex — незаякоренное регулярное выражение.
Результат совпадает. Якоря добавлять нельзя: claude-code перейдёт в режим regex и поведение разъедется.

### 3. Защита встроенной проверки

Событие: `PreToolUse`, тот же matcher.
Команда: `wk hook guard-paths`.
Действие: **код 2**, если `tool_input.file_path` — один из:

| путь | причина |
|---|---|
| `docs/_meta/check.py` | проверяющий инструмент не правится тем, кого он проверяет |
| `.claude/settings.json` | там живут сами хуки |
| `.codex/hooks.json` | там живут сами хуки |
| `.wiki-project.yaml` | оттуда хуки берут, что защищать |

`.codex/hooks.json` обязателен в списке: без него на codex этот пункт не выполняется вовсе —
защита снимается удалением собственного конфига.

`.wiki-project.yaml` обязателен по той же причине, на уровень глубже. `guard-block` берёт
список защищаемых файлов из `policy_blocks` манифеста, `policy-stale` и `check` — параметры
компиляции. Манифест без защиты — это выключатель всех трёх: стёр `policy_blocks`, и блок
политик стало можно править. Никакая команда `wk`, кроме `init`, манифест не пишет
(`wk/internal/wk/init.go:201`), а `init` пишет его сам, минуя инструменты харнесса, —
поэтому запрет ничего не ломает. Правит манифест человек.

`.claude/settings.local.json` **не** защищается: личные настройки человека, вне git.

После задачи 06 `check.py` в проекте не нужен вовсе — хук остаётся как страховка от его возвращения.

### 4. Напоминание о политиках на старте

Событие: `SessionStart`, matcher `startup|resume`.
Команда: `wk hook policy-stale`.

Блок устарел — печатает на stdout ровно это:

```json
{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "Политики компании изменились, выполни `wk policy sync`."}}
```

Блок актуален или сети нет — пустой stdout. **Код выхода всегда 0.**

Не блокирует, не синхронизирует сам: сеть на старте сессии не должна ломать работу офлайн.

Почему не `wk policy check` напрямую: эта команда возвращает 1 при недоступности политик,
а ненулевой код на `SessionStart` у обоих харнессов — неблокирующая ошибка, то есть шум в журнале
при каждом старте в офлайне. И текст надёжно попадает в контекст модели только через
`hookSpecificOutput.additionalContext`: поведение простого текста на stdout у claude-code
оговорено как «на некоторых событиях», у codex не описано. `wk policy check` остаётся
человеческой командой, `wk hook policy-stale` — точкой входа для харнесса.

## Требования к реализации

- все хуки вызывают только `wk`. Никаких `python`, `jq`, `sed`, многострочных shell-скриптов в JSON;
- хуки записи завершаются не дольше 5 секунд и сети не касаются;
- `wk hook check` и `wk hook policy-stale` обращаются к вике за версией блока политик,
  поэтому их `timeout` — 10 секунд, а недоступная сеть даёт код 0, а не отказ;
- хук без манифеста `.wiki-project.yaml` молча выходит с кодом 0: в не-проектных репозиториях он не мешает;
- тексты отказов — одна строка, с конкретным действием, без воды;
- конфигурация создаётся `wk init`; существующие `.claude/settings.json` и `.codex/hooks.json`
  не перезаписываются, печатается diff и предложение применить руками;
- два хука записи сводятся в одну группу `PreToolUse` с общим matcher: у обоих харнессов
  несколько команд в группе выполняются вместе, и кода 2 от любой достаточно для блокировки.

## Для агентов без хуков

Те же четыре проверки ставятся в CI проекта как обязательный шаг:

```
wk check --strict
```

Обратная связь медленнее, непробиваемость та же. `wk init` кладёт заготовку workflow с этим шагом.

## Тесты

В `cli/`:

1. `wk hook guard-block` на правке внутри блока — код выхода 2 и текст с подсказкой;
2. то же вне блока — код 0;
3. `wk hook guard-block` на файле, которого нет в `policy_blocks` — код 0;
4. все хук-подкоманды без манифеста — код 0 и пустой вывод;
5. `wk check --strict` на проекте с устаревшим блоком — код 1;
5a. `wk hook check` на том же проекте — код **2** и одна строка в stderr;
5b. `wk hook check` при недоступной вике — код 0 и предупреждение в stderr; ход не блокируется;
5c. `wk hook check` с `stop_hook_active: true` в payload — код 0, проверки не запускались
    (проверять по отсутствию обращения к `httptest.Server`);
6. `wk hook guard-paths` на каждом из четырёх защищённых путей — код 2; на произвольном файле — код 0;
7. хук-подкоманды читают путь из stdin: payload без `tool_input.file_path`, с лишними неизвестными
   полями и с обрезанным JSON — код 0 и пустой вывод, падения нет;
8. `wk hook policy-stale` при устаревшем блоке — код 0 и ровно один JSON-документ
   с `hookSpecificOutput.additionalContext`; при актуальном и при недоступной сети — код 0 и пустой stdout;
9. `hooks/install/claude-settings.json` и `hooks/install/codex-hooks.json` — валидный JSON,
   все четыре хука на месте, в каждой команде только `wk`, `type` везде `command`.

## Готово, когда

- `wk init` раскладывает `.claude/settings.json` и `.codex/hooks.json` со всеми четырьмя хуками;
- каждый хук — одна команда `wk` типа `command`, путь берётся со stdin;
- попытка агента отредактировать блок политик, `check.py`, `.claude/settings.json`,
  `.codex/hooks.json` или `.wiki-project.yaml` блокируется, проверено тестом;
- `cli/README.md` — раздел «Хуки» с таблицей событие → команда → поведение и строкой про stdin.

## Не делать

- не ставить хук, который автоматически делает `wk policy sync` или коммитит;
- не писать логику хука shell-выражением внутри JSON;
- не блокировать запись файлов, не перечисленных в этой задаче;
- не использовать `${CLAUDE_PROJECT_DIR}`, `args`, `if`, `once`, `http`/`prompt`/`agent`:
  в codex этого нет, общий фрагмент разъедется на два;
- не ставить `wk check --strict` командой хука напрямую: код 1 не блокирует, и гейт станет украшением;
- не блокировать завершение хода из-за недоступной сети и не игнорировать `stop_hook_active`:
  и то, и другое запирает агента в ходе, который он не может завершить.
