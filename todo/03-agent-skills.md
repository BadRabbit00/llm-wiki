# 03 — Скиллы для агентов

## Цель

Короткие, предсказуемые входы в пайплайн «дока → код». Вся логика в `wk` (задача 02),
скилл — тонкая инструкция, когда и в каком порядке его вызывать.

## Где лежат

Эталонные копии — в репозитории `skills/` (рядом с `backend` и `wk`), по папке на скилл.

`wk init` раскладывает их в **проект**, не в этот репозиторий:

| харнесс | каталог в проекте | явный вызов |
|---|---|---|
| claude-code | `.claude/skills/<name>/SKILL.md` | `/<name>` |
| codex | `.agents/skills/<name>/SKILL.md` | `$<name>` |

Один и тот же файл копируется в оба каталога. Именно копией, не симлинком: `wk` отвергает
симлинки на любом участке пути при записи проектных файлов, и это правило не ослабляется
ради удобства раскладки.

Скиллы встраиваются в бинарь `wk` так же, как скелет docs-kit: `wk init --offline`
обязан работать, а сеть на раскладку скиллов тянуть незачем.

Версионируются вместе с проектом.

## Формат один на оба харнесса

Каталог `<name>/SKILL.md`, YAML-frontmatter, тело в Markdown — совпадает у обоих.
Отличается только путь установки.

Frontmatter ограничен **двумя полями**: `name` и `description`. Оба обязательны в codex;
claude-code не требует ничего, но выбирает скилл по той же `description`.

Всё остальное, что умеет claude-code — `allowed-tools`, `context: fork`, `agent`, `model`,
`effort`, `paths`, `hooks`, `argument-hint`, инъекция вывода команд через `` !`cmd` `` —
в codex не документировано. Любое такое поле превращает общий файл в два разных.
Ограничение уместно: вся логика живёт в `wk`, скиллу нужен только текст.

`name` обязан совпадать с именем каталога.

### Ловушка YAML, которая молчит

`description` — плоский скаляр. Двоеточие с пробелом внутри него обрывает значение,
и харнесс загружает скилл с пустыми метаданными **без ошибки**: codex игнорирует
некорректный frontmatter молча. Писать `doc:<ID>`, а не `doc: <ID>`; либо брать всё
значение в кавычки. Проверяется автоматически, см. «Проверка».

Источники: `https://code.claude.com/docs/en/skills`, `https://learn.chatgpt.com/docs/build-skills`.

## Общие требования к каждому скиллу

- `description` — одна строка, и в ней сказано, **когда вызывать и когда не вызывать**:
  codex требует именно этого, claude-code по этой же строке выбирает скилл;
- `description` вместе с дополнительным контекстом не длиннее 1536 символов: у claude-code
  это жёсткий потолок в списке скиллов, у codex общий бюджет списка — 2% контекста или 8000 символов;
- тело: пронумерованные шаги, императив, без объяснений «почему» и без примеров на три экрана;
- вся работа с сетью и файлами — через `wk`. Скилл **не** содержит `curl`, не содержит URL вики,
  не содержит имён переменных с токеном;
- скилл не пишет «при необходимости», «желательно», «обычно». Только обязательные шаги;
- каждый скилл заканчивается шагом `wk check --strict`.

## Состав

### `policy-sync`

> Обновить правила компании в проекте перед работой.

1. `wk policy sync`
2. `wk doctor`
3. Изменился `AGENTS.md` — прочитать блок между `<!-- wikisvc:begin … -->` и `<!-- wikisvc:end -->` целиком.
4. Блок не трогать руками. Это сгенерированный текст.

### `doc-card`

> Завести или изменить факт в документации проекта.

1. Определить тип факта и префикс ID по `docs/_meta/ids.md`. Новых префиксов не придумывать.
2. Определить файл по таблице в `ids.md`. ID определяется ровно в одном месте.
3. Создать карточку или строку таблицы по `docs/_meta/format.md`. Статус — `draft`.
4. Не уверен в значении поля — `Q-…` в `docs/open-questions.md` и ссылка на него из карточки.
   Догадка в карточку не пишется.
5. Перевод `draft` → `planned` делает человек. Агент этого не делает.
6. `wk check --strict`

### `implement-planned`

> Реализовать факты со статусом `planned`.

1. `wk policy sync`
2. Прочитать `docs/INDEX.md`, `docs/system/overview.md`, `docs/system/domain.md`.
3. Прочитать `docs/components/<компонент>/component.md` и файлы по ссылкам из него.
4. Выбрать факты со статусом **`planned`**. Факты в `draft` не реализуются.
5. Написать код. Поставить маркер `doc:<ID>` в каноническом месте по таблице в `docs/_meta/workflow.md`.
6. Перевести статус факта в `implemented`.
7. Не хватает факта, которого нет в документации — остановиться, вызвать скилл `doc-card`,
   в код молча не добавлять.
8. `wk check --strict`

### `propose-rule`

> Предложить правило в общую вику, когда в политиках пробел.

1. Убедиться, что правила нет: `wk policy search "<суть>"`.
2. Написать файл по шаблону правила: разделы «Правило», «Обоснование», «Примеры».
   Поля `category`, `level`, `applies_to`, `origin` обязательны.
3. `wk propose --file <path>`
4. Напечатать `pid` и ссылку. Решение принимает человек в UI.
5. Не ждать принятия, не опрашивать статус в цикле, продолжить работу по текущим политикам.

### `audit-docs` — не в первой версии

Сверка документации с политиками (задача 07B) запускается **из UI**, где есть человеческая сессия:
`wikiagent` не принимает анонимные вызовы (`src/wikiagent/api.py:86-91`, задача 09).
Скилл появится, когда у человека на ноуте будет сессионный токен.

Исправления по найденным расхождениям оформляются обычным `doc-card`, по одному факту за раз.

## Агенты без поддержки скиллов

claude-code и codex скиллы поддерживают, и раскладка выше покрывает оба. Для всего остального
`wk init` дописывает в `AGENTS.md` раздел:

```markdown
## Команды проекта

- перед задачей: `wk policy sync && wk doctor`
- новый факт в документации: статус `draft`, ID по `docs/_meta/ids.md`, неизвестное — в `Q-…`
- реализация: только факты `planned`, маркер `doc:<ID>`, затем статус `implemented`
- пробел в политиках: `wk propose --file <path>`
- в конце работы: `wk check --strict`
```

Этот раздел — вне блока `wikisvc:begin/end`, он не перезаписывается синхронизацией политик.

## Проверка

Разбор и проверка скиллов — подкомандой `wk`, не отдельным скриптом в репозитории:
проверяющий инструмент должен быть скомпилирован, иначе модель его поправит (та же причина,
что в задаче 06). Место — `wk doctor`, предупреждением, и `wk init`, отказом до записи.

Проверяется:

1. первая строка файла — `---`, frontmatter разбирается как YAML;
2. поля ровно `name` и `description`, посторонних нет;
3. `name` совпадает с именем каталога;
4. `description` непустой, одна строка, не длиннее 1536 символов;
5. последний шаг тела содержит `wk check --strict`;
6. в файле нет `curl`, URL со схемой, имени переменной токена и слов
   «желательно», «обычно», «при необходимости».

## Готово, когда

- скиллы лежат в репозитории `skills/`, встроены в бинарь и раскладываются `wk init`
  в `.claude/skills/` и `.agents/skills/` одновременно;
- в каждом есть frontmatter из двух полей и последний шаг `wk check --strict`;
- ни один скилл не содержит URL, токенов, `curl` и слова «желательно»;
- `wk doctor` проверяет скиллы по списку выше и падает на `description` с `: ` внутри;
- `cli/README.md` — раздел «Скиллы» с таблицей скилл → когда вызывать и двумя путями раскладки.

## Не делать

- не дублировать в скиллах правила из `docs-kit/AGENTS-snippet.md` — ссылаться;
- не писать скиллы, которые принимают предложения или меняют статус факта в обход человека;
- не делать скилл-«оркестратор», запускающий остальные скиллы;
- не добавлять в frontmatter поля, которых нет в codex: общий файл разъедется на два;
- не складывать проверку скиллов отдельным скриптом в проект — только в бинарь `wk`.
