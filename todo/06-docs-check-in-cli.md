# 06 — Проверка документации внутри `wk`

## Цель

Проверка `docs/` компилируется в бинарь `wk`. Агент не может её изменить, ослабить или удалить:
в репозитории проекта проверяющего кода больше нет.

## Исходная спека

`/home/BadRabbit/work/docs-kit/docs/_meta/check.py`, 464 строки, Python 3.9+, только стандартная библиотека.
Это **единственный источник требований**. Семантика переносится один в один, включая русские тексты
сообщений, порядок вывода и коды выхода.

## Команды

- `wk docs check [--docs docs] [--code .] [--strict] [--no-registry] [--json]` — полная проверка;
- `wk check [--strict]` — то же плюс проверка свежести блока политик (задача 07).

Коды выхода: `0` — чисто; `1` — есть ошибки или (`--strict`) предупреждения; `2` — неверные аргументы;
`3` — не найден `docs/` или манифест.

## Что переносится (по разделам исходника)

### Правила размещения ID

- таблица `LOCATION`: три вида правил — конкретный файл, `("component", "<файл>.md")`, `("dir", "decisions/")`;
- `RULE` заменён на `INV` (задача 05);
- `PREFIXES` сортируются по длине по убыванию — порядок влияет на регулярку, сохранить;
- `GROUPS` — порядок секций реестра;
- `STATUS_DEFAULT`, `STATUS_BY_PREFIX` (у `TERM` статуса нет), `OWNED`, `CODE_TYPES = OWNED`;
- бюджеты строк: `INDEX.md` 150, `components/*/component.md` 120, остальное 400;
- `TITLE_COLUMNS` — порядок важен, берётся первая найденная колонка;
- `SKIP_CODE_DIRS` — список целиком.

### Регулярные выражения

Переносятся с тем же поведением. Go `regexp` не поддерживает lookbehind `(?<![\w-])` из `REF_RE` —
заменить проверкой символа перед совпадением вручную, результат должен совпадать на тестах.

| имя | назначение |
|---|---|
| `REF_RE` | ссылка: ID, необязательные `.*` и `#часть` |
| `FULL_ID_RE` | строка целиком — ID |
| `HEADING_RE` | заголовок markdown |
| `HEAD_DEF_RE` | `ID — Название` в заголовке |
| `MARKER_RE` | `// # -- /* <!-- ;` + `doc:` |
| `CELL_SPLIT_RE` | разделение ячеек по `|`, экранированное `\|` не разделяет |

### Разбор `docs/`

- `doc_files`: `*.md` рекурсивно, отсортированные; пропускать пути, где любая **родительская** часть
  начинается с `_` (`_meta`, `components/_template`); пропускать файлы со `template` в имени (без регистра);
- отслеживание тройных кавычек: внутри ``` заголовки и таблицы не разбираются;
- карточка: заголовок уровня ≤ 4 вида `ID — Название`; мета-строка — **первая непустая** строка после заголовка;
  карточка закрывается заголовком того же или более высокого уровня;
- `parse_meta`: пары `ключ: значение` через ` | `; ключ приводится к нижнему регистру, снимаются обратные кавычки;
  ключ не соответствует `[a-z_]+` или нет `:` — мета-строка считается отсутствующей (пустой словарь);
- таблица: первая строка — заголовки; строка-разделитель из `-` и `:` пропускается;
  определения берутся только если первая колонка называется `id`;
- если у таблицы нет заголовка `id`, но первая ячейка — полный ID: **ошибка** с текстом про лишнюю пустую строку;
- ссылки: собираются из всех строк; `user` — ID текущей строки-определения, иначе ID карточки, иначе путь файла;
  ссылка карточки на саму себя не считается; само определение в своей строке не считается ссылкой;
- дубль ID — ошибка с указанием места первого определения.

### Проверки

- место определения не совпало с `LOCATION` → **предупреждение** с ожидаемым местом;
- нет `status` или значение не из допустимого набора → ошибка;
- `replaced_by` указывает на неопределённый ID → ошибка;
- тип из `OWNED` без `owner` → ошибка; `owner` не определён или не `SVC-`/`LIB-` → ошибка;
- `owner` не совпадает с владельцем папки компонента → предупреждение;
- ссылка на неопределённый ID → ошибка; шаблон `PREFIX-scope.*` ни на что не подходит → ошибка;
- превышен бюджет строк → предупреждение.

### Сканирование кода

- обход от `--code`, каталог `docs/` исключается по разрешённому пути;
- пропуск: файлы больше 2 000 000 байт, бинарные (нулевой байт в первых 4096), не содержащие `doc:`;
- декодирование UTF-8 с игнорированием ошибок;
- маркер на неизвестный ID → ошибка;
- `implemented` у типа из `CODE_TYPES` без маркера → предупреждение;
- маркер при статусе `draft`/`planned` → предупреждение с местом маркера;
- маркер при `deprecated` → предупреждение.

### Реестр

`docs/_meta/registry.md` генерируется с тем же заголовком, той же строкой итогов, теми же секциями
и теми же колонками. `short()` обрезает списки: места в коде до 3, использующих до 6, остаток как `+N`.
Пути оборачиваются в обратные кавычки. `|` в названии экранируется.

Плюс новая секция «Политики компании» из задачи 05.

### Вывод

```
ОШИБКА  <файл>:<строка>: <текст>
ВНИМАНИЕ <файл>:<строка>: <текст>

ID: N, ссылок: N, маркеров в коде: N, ошибок: N, предупреждений: N
```

Порядок: сначала все ошибки, потом все предупреждения — как в исходнике.

## Приёмочный тест — обязательный

Golden-тест против исходной реализации:

1. вход — `/home/BadRabbit/work/docs-kit/example` (после правок задачи 05);
2. эталон — вывод `python3 example/docs/_meta/check.py` и содержимое сгенерированного `registry.md`;
3. `wk docs check` на том же входе даёт **побайтово совпадающий** stdout и `registry.md`;
4. эталоны положить в `cli/testdata/`, вход — копией в `cli/testdata/example/`;
5. то же для `--strict` и для случая с внесёнными поломками (дубль ID, битая ссылка, маркер на draft,
   таблица без заголовка `id`, превышенный бюджет) — по одной поломке на тест-кейс.

Без побайтового совпадения задача не принимается.

## Миграция проектов

- `docs-kit/docs/_meta/check.py` **удалить** из шаблона;
- `docs-kit/docs/_meta/workflow.md` раздел «Проверка»: команды заменить на `wk check` и `wk check --strict`;
- `docs-kit/README.md`: строку про `check.py` заменить на `wk`;
- `wk docs upgrade`: обнаружив `docs/_meta/check.py` в проекте, удаляет его и печатает одну строку
  «проверка теперь встроена в wk»;
- `docs/_meta/registry.md` остаётся генерируемым файлом в проекте и коммитится.

## Готово, когда

- `wk docs check` побайтово совпадает с эталоном на `example`;
- `check.py` отсутствует в `docs-kit`;
- `go test ./...` и `go vet ./...` зелёные;
- хук из задачи 04 блокирует создание `docs/_meta/check.py`.

## Не делать

- не «улучшать» проверки, не добавлять новых правил, не менять тексты сообщений;
- не менять формат `registry.md`, кроме новой секции из задачи 05;
- не делать проверку конфигурируемой файлом в проекте: набор правил жёсткий, иначе агент его ослабит;
- не оставлять в `wk` флага, отключающего отдельные проверки.
