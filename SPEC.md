# llm-wiki — свод правил компании для агентов, которые пишут код

Спецификация системы. Этот файл — источник правды о том, **что** система делает и
**зачем**. Как её поставить, настроить и чем пользоваться — [GUIDE.md](GUIDE.md);
подробности реализации — в README каждого репозитория.
Если документ и код расходятся — расходится документ, и его правят в том же коммите.

---

## 1. Задача

В компании есть решения о том, как писать код: какой стек, как обрабатывать ошибки,
что логировать, как тестировать, что нельзя делать никогда. Эти решения живут
в головах, чатах и устаревших `AGENTS.md`, по-разному скопированных в двадцать репозиториев.

Агент, который пишет код, не знает их. Человек, который ревьюит агента, тратит время
на одни и те же замечания. Через полгода никто не помнит, почему правило появилось.

Система решает три задачи:

1. **Хранить** правила так, чтобы у каждого были ID, версия, обоснование, источник
   и история изменений.
2. **Доставлять** их агенту в том объёме, который относится к его проекту, и в том
   виде, который влезает в контекст.
3. **Не давать** правилам расходиться с реальностью: проверять проект на соответствие
   и ловить противоречия внутри самого свода.

Главный инвариант: **решения принимает человек.** Агент предлагает, человек решает.
Ни один автоматический путь не ведёт к принятию, повышению, отмене или откату правила.

## 2. Из чего состоит

Шесть каталогов в `work/`, каждый — отдельный Git-репозиторий, плюс репозиторий
контента, который локально не держат: он живёт там, где запущен сервис.

| каталог | что это | язык |
|---|---|---|
| вика | **контент**: страницы правил, схема, сырьё. Источник правды. Живёт на сервере; локально заводится `wikisvc init <путь>` | Markdown + YAML |
| `llm-wiki/` | `wikisvc` — детерминированное ядро, `wikiagent` — работа с моделью, `ui/` — веб-интерфейс, и эти три документа | Python 3.12, Go, React |
| `wk/` | CLI, который живёт в репозитории **проекта**, а не вики | Go |
| `../docs-template/` | скелет документации проекта со стабильными ID | Markdown |
| `../skills/` | навыки агента — названные процедуры для claude-code и codex | Markdown |
| `../hooks/` | хуки агента — конфигурация харнессов | JSON |
| `../mainserver/` | установка сервера (btrfs, Arch). К llm-wiki не относится | shell |

Разделение контента и кода не косметика: контент переживает код. Его можно
клонировать, читать и править без запущенного сервиса, и он версионируется сам собой.

### 2.1. `wikisvc` — ядро

Детерминированный сервис. **Не вызывает LLM и не делает исходящих сетевых запросов.**
Одноузловой: запись сериализуется `fcntl.flock` по локальному файлу.

- хранилище — Git-репозиторий вики; записи идут через worktrees и атомарные коммиты;
- `state.db` (SQLite) — токены, предложения, находки, аудит, счётчики;
- `wiki.db` (SQLite FTS5) — производный индекс, пересобирается командой;
- HTTP API `/api/v1` (FastAPI) и MCP — stdio и Streamable HTTP;
- CLI: `init`, `serve`, `mcp`, `token`, `policies`, `reindex`, `lint`, `migrate-rules`,
  `schema upgrade`, `repair-worktrees`.

### 2.2. `wikiagent` — всё, что требует модели

Отдельный процесс и отдельный клиент ядра. Говорит с моделью через совместимый
`/v1/chat/completions`; роли `planner`, `reviewer`, `chat` настраиваются независимо.

Три вида фоновых задач с контрольными точками:

- `ingest-book` — читает загруженную книгу по главам и готовит кандидатов в правила;
- `heal` — ищет противоречия внутри вики и пишет находки с предложениями;
- `docs_audit` — сверяет `docs/` конкретного проекта с действующими политиками.

Анонимные вызовы не принимает никогда. Допуск вызывающего обязан быть не ниже допуска
рабочего токена агента: через агента нельзя получить то, чего не видно напрямую.

### 2.3. `ui/` — веб-пространство

Go-бинарник со встроенными ресурсами плюс React SPA. Вход только через OIDC
(Authentik); сессия — HttpOnly/Secure cookie, JavaScript токена не видит.
База знаний, чат, редактор, ревью, библиотека, граф, экспорт инструкций, задачи.

### 2.4. `wk` — CLI в репозитории проекта

Единственный инструмент, который разработчик и агент проекта запускают у себя.
Стандартная библиотека Go плюс `yaml.v3`, статический бинарник, без зависимостей.

```
wk init        создать проект из шаблона вики
wk doctor      диагностика: манифест, связь с викой, свежесть политик
wk component add   добавить компонент с документацией
wk docs check  проверка документации проекта
wk check       то же плюс свежесть блока политик
wk policy sync вписать актуальный блок политик в AGENTS.md
wk policy check устарел ли блок
wk policy search|show   найти и прочитать правило
wk propose     отправить правку правила в вику предложением
wk template list|show   шаблоны проектов
```

Чего у `wk` нет и не будет: команд принятия, повышения, отмены и откатa правил.

## 3. Модель данных

### 3.1. Страница правила

Тип `rule` в вике. Обязательные поля frontmatter:

| поле | смысл |
|---|---|
| `summary` | один тезис, 20–160 символов — то, что попадёт в инструкцию агенту |
| `category` | stack, security, errors, logging, testing, architecture, code-style, git, build-ci, docs, process |
| `level` | `must` — нарушать нельзя; `should` — по умолчанию да; `idea` — обсуждается |
| `lifecycle` | `candidate` → `active` → `deprecated` |
| `applies_to` | список scopes или `*` |
| `origin` | откуда взялось |

Разделы текста: «Правило», «Обоснование», «Примеры», необязательные «Исключения».
`must` требует владельца и источник решения. Активное правило подтверждено человеком
(`verified_by`). Поля `lifecycle`, `level`, `priority`, `owner`, `verified_*` защищены:
PATCH их не меняет, PUT сохраняет прежние значения.

### 3.2. Scopes и профили

`scope` — координата проекта: `lang:python`, `framework:fastapi`, `app:orders`.
`profile` — именованный набор scopes плюс бюджет токенов: `python-fastapi`, `go-service`.
И то и другое ведёт администратор в `wiki/schema/`; через предложения не меняется.

### 3.3. Блок политик

Политики попадают в репозиторий проекта **только** сгенерированным блоком:

```
<!-- wikisvc:begin version=a3f91c2e -->
… компактный список действующих правил …
<!-- wikisvc:end -->
```

Версия — хеш от содержимого правил и параметров компиляции. Агент на правило
**ссылается** по ID, его текст **не пересказывает**: пересказ нельзя сверить,
у него нет версии, и он расходится с оригиналом молча.

В инструкцию входят только активные `must` и `should` с пересекающимися scopes.
Все `must` сохраняются даже сверх бюджета (`over_budget=true`). Машинно проверяемые
`should` по умолчанию опускаются — их нарушение поймает CI.

### 3.4. ID документации проекта

`docs-template` даёт скелет со стабильными ID: `SVC-`, `LIB-`, `INV-` (инвариант домена),
`ADR-`, `TERM-` и прочие. В коде на факт ссылается маркер `doc:<ID>` в комментарии.
Проверка связывает три вещи: ID определён в документации, на него ссылаются, он
реализован в коде. Расхождение — ошибка или предупреждение с файлом и строкой.

**`INV-` и `rule-` — разные факты.** Инвариант домена принадлежит проекту; политика
компании принадлежит вике и в проекте только упоминается. Раньше оба писались `RULE-`
и `rule-`, и человек, читающий документ, не мог их различить.

## 4. Как этим пользуется человек

### 4.1. Правило родилось в разговоре

1. Человек открывает чат в UI, выбирает профиль и пишет как есть:
   «мы используем FastAPI и только async-код».
2. Планировщик возвращает **план**: тезисы, diff страницы, влияние на профили,
   допущения и блокирующие вопросы. Ответ в той же сессии уточняет черновик.
3. Человек проверяет план и принимает предложение. Сам агент этого сделать не может.
4. Новое правило от агента всегда инертное: `candidate`, `should`, `priority 3`.
   Чтобы оно попало в инструкции, человек повышает его отдельным действием —
   и для `must` обязан указать владельца и источник решения.

### 4.2. Правило родилось из книги

Человек загружает книгу в библиотеку, запускает `ingest-book`, и задача читает её
по главам. Полный текст в вику не попадает — остаются библиография, выжимка и
короткие проверяемые цитаты. Кандидаты ждут решения человека.

### 4.3. Новый проект

```sh
wk init --url https://wiki.company --profile go-service --template go-service
```

Из вики приезжает шаблон: скелет `docs/`, `flake.nix`, `.gitignore`, запись
`policy_blocks` в манифесте `.wiki-project.yaml`. Затем `wk policy sync` вписывает
актуальный блок политик в `AGENTS.md`, и агент в этом репозитории видит правила
компании с первой минуты.

Шаблон — это удалённый генератор кода, поэтому он **данные, и только данные**:
поля вида `post_init`, `exec`, `script`, `command` не разбираются вовсе, пути
проверяются до записи, симлинки не создаются, лимиты 200 файлов / 2 МиБ / 256 КиБ.

### 4.4. Повседневная работа в проекте

- `wk check` перед коммитом: документация согласована, блок политик свежий;
- `wk check --strict` в CI: предупреждения тоже считаются ошибками;
- политики изменились — `wk policy sync`, одна строка diff на файл;
- нужно поспорить с правилом — `wk propose`, а не правка блока руками.

### 4.5. Разбор находок

Находки от `heal` и `docs_audit` ложатся во входящие. Человек их закрывает:
`dismiss` **требует причины** и держится до изменения текста правила. Статистика
по виду находок рекомендует поднять порог уверенности, если отклонено больше
половины — но сама порог не меняет. Это тоже решение человека.

## 5. Как этим пользуется агент

Через MCP (20 инструментов, профиль `coding` — 13) или HTTP. Порядок работы:

1. `get_instructions` — всегда первым;
2. `get_policies(profile)` — компактный свод действующих правил под задачу;
3. `get_rule(id)` — подробности, исключения и связи того правила, которое мешает;
4. `rules_related`, `graph_impact` — что ещё затронуто.

Операций принятия, повышения, снятия и отката у агента нет ни в одном транспорте.

### 5.1. Навыки и хуки

Правила из `AGENTS.md` — просьба, которую модель может проигнорировать. Поэтому то,
что проверяется детерминированно, проверяется стеной:

- **навыки** (`../skills/`) — названные процедуры, которые человек вызывает `/name`
  или `$name`. Каждая заканчивается `wk check --strict`;
- **хуки** (`../hooks/`) — команды харнесса. `PreToolUse` блокирует правку блока политик,
  проверяющего инструмента, конфигурации хуков и манифеста. `SessionStart` напоминает
  об устаревших политиках. `Stop` не даёт завершить ход, пока проверки не прошли.

Формат навыка переносим между claude-code и codex, контейнер хуков — нет: у первого
`.claude/settings.json`, у второго `.codex/hooks.json`. Поэтому содержимое групп
одинаковое, а файлов два.

## 6. Границы, которые нельзя нарушать

Это инварианты продукта, а не стиль. Каждый существует потому, что без него система
перестаёт быть тем, чем задумана.

1. **Решения принимает человек.** `require_human()` требует `kind == "human"`.
   Ни агент, ни автоматический путь не получают `accept`, `promote`, `deprecate`,
   `revert`, `dismiss`.
2. **Автор не принимает своё предложение.** Сравнивается стабильная identity, а не
   имя токена: перевыпуск токена не превращает автора в постороннего ревьюера.
3. **Новое правило от агента инертно:** `candidate`, `should`, `priority 3`.
4. **Ядро детерминировано.** `wikisvc` не вызывает LLM и не делает исходящих запросов.
5. **Одноузловость.** Блокировка записи — локальный файл. Система не проектируется
   под несколько машин.
6. **Внешние данные недоверенные.** Ответы модели, книги, загруженные файлы и
   проектные документы проверяются, помечаются `untrusted_external` и не исполняются.
   Инструкции внутри них игнорируются.
7. **Потолок анонимного доступа задаётся кодом.** Анонимный принципал всегда
   `kind=agent`, роль не выше `writer`, допуск не выше `internal`. Конфигурация может
   только понизить. Следствие: `restricted` закрыт, решения недоступны.
8. **Политика попадает в проект только блоком с версией.** Пересказ запрещён.
9. **Проверяющий код не лежит в проверяемом репозитории.** Проверка скомпилирована
   в бинарь `wk`, чтобы тот, кого проверяют, не мог её ослабить.
10. **Секреты не доезжают до диска и логов.** Детектор энтропии работает до сохранения;
    токен вычищается из каждого потока и не следует за редиректом на другой хост.

## 7. Права доступа

Роли `reader` → `writer` → `reviewer` → `admin`.
Допуск `public` → `internal` → `restricted`.

Недоступная страница даёт **404**, а не 403, и исчезает из поиска, контекста, графа,
истории, индекса и предложений: разница между «нет» и «не для тебя» сама является
утечкой. Авторизация предшествует чтению тела запроса. Человеческие сессии выдаёт
служебный токен UI через OIDC; постоянные токены — CLI, они показываются один раз,
в базе только хеши.

## 8. Развёртывание

Один узел с systemd, сборка через Nix. `nix build .#deployment` даёт установщик,
четыре службы (`wikisvc`, `wikiagent`, `wiki-ui`, локальная модель), конфигурацию,
проверку готовности и восстановление worktrees после переноса.

Бэкап обязателен и снимается **на остановленных службах**: SQLite и worktrees
в горячем режиме дают рваный архив, который выглядит целым до дня восстановления.
Копируются контент, `STATE_DIR` и `WIKIAGENT_STATE_DIR`; индекс не копируется —
он пересобирается. Непроверенная копия копией не считается.

Самолечение и сверка документации выключены по умолчанию и включаются человеком
после первого ручного цикла.

## 9. Что намеренно не делается

- OCR сканов, эмбеддинги, графовая БД — поиск только BM25 плюс граф связей;
- мультиузловое развёртывание;
- `wk audit` и любой клиентский путь к `wikiagent` без человеческой сессии:
  это обошло бы сравнение допусков;
- предложения из находок `docs_audit` — пока только находки;
- второе написание для политик (`POL-` рядом с `rule-`): два написания одного
  факта хуже одного неудобного.
