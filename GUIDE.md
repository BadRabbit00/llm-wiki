# llm-wiki — руководство пользователя

Как поставить, настроить и работать. Для администратора сервера, для человека,
который ведёт правила, и для разработчика, который их получает в своём проекте.

Что это за система и зачем — в [SPEC.md](SPEC.md). Открытые дефекты — в [fix.md](fix.md).
Здесь только практика: команды, параметры, экраны, порядок действий.

**Коротко.** Компания держит правила написания кода в Git-вики с версиями,
обоснованиями и историей. Система доставляет их агенту в объёме его проекта,
проверяет проект на соответствие и ловит противоречия внутри самого свода.
Решения принимает человек — ни один автоматический путь не меняет правило.

# 1. Установка на сервер

## 1.0. Что понадобится

**Железо.** Сервис сам по себе скромен: CPU, пара гигабайт памяти, диск под
контент и индекс. Требовательна только локальная модель — ей нужен GPU
с достаточной VRAM под выбранный GGUF и квантование.

**Система.** Linux с systemd. NixOS **не** требуется. Проверено на Arch, подходят
Debian, Ubuntu и другие. Нужны: Bash, `sudo`, Git, `curl`, `xz`, GNU `tar`/`gzip`/`find`,
util-linux (`runuser`, `flock`, `getent`), средства создания пользователей
(`useradd`, `groupadd`, `usermod`). Имена пакетов зависят от дистрибутива —
поставьте их своим пакетным менеджером **до** установки.

Всё остальное — Python, Go, Node, зависимости — приносит Nix из `flake.lock`.
Входить в `nix develop` на сервере не нужно.

**Без systemd** автоматический установщик не работает. Собирайте `nix build .#wikisvc .#ui`
и запускайте под своим супервизором, передавая то же окружение и тех же пользователей.

**Куда всё встанет:**

```text
/opt/llm-wiki/current       установленный bundle (постоянный Nix GC root)
/opt/llm-wiki/previous      предыдущий bundle — для откатa
/etc/llm-wiki/              service.env, agent.env, wikiagent.yaml, llama.env,
                            ui.env, backup.env, roles.yaml, секреты
/var/lib/llm-wiki/
  wiki/                     репозиторий контента, включая .git
  state/                    state.db, worktrees, библиотека, кэш извлечений
  agent/                    agent.db, сессии, задачи
  index/                    производный индекс — пересобирается
/var/backups/llm-wiki/      резервные копии (root, 0700)
/srv/llm-wiki/models/       GGUF (вне Git и вне Nix store)
```

Четыре службы: `wikisvc` (ядро), `wikiagent` (работа с моделью), `wiki-ui`
(веб-интерфейс), `llm-wiki-model` (llama-server). Каждая — от своего системного
пользователя, все API слушают loopback.

## 1.1. Nix и сборка

```sh
# Nix, если его ещё нет — по официальному руководству https://nix.dev/install-nix
curl --proto '=https' --tlsv1.2 -sSfL https://nixos.org/nix/install -o /tmp/install-nix.sh
sh /tmp/install-nix.sh --daemon      # просмотрите скрипт перед запуском
# откройте новую оболочку
nix --version

git clone git@github.com:BadRabbit00/llm-wiki.git
cd llm-wiki
nix --extra-experimental-features 'nix-command flakes' \
  build .#deployment --out-link result-deployment
sudo ./result-deployment/bin/llm-wiki-install
```

Для обычного сервера ставьте multi-user daemon. На машине с SELinux проверьте
поддержку политики выбранным способом установки Nix — установщик проекта
не меняет ни SELinux, ни firewall.

Сборка прогоняет pytest, Ruff, mypy, ShellCheck, TypeScript и Go-тесты, поэтому
первая занимает время. `nix flake update` при установке не нужен: `flake.lock`
уже в репозитории.

Установщик создаёт пользователей, каталоги, конфигурацию и unit-файлы.
**Существующие конфиги и контент он не перезаписывает** — при обновлении новые
параметры из `deploy/linux/service.env` и `ui.env` добавляйте вручную.
Службы он не запускает: сначала настройка.

## 1.2. Новая вики или перенос существующей

Новая установка:

```sh
sudo /usr/local/sbin/llm-wiki-admin wikisvc init /var/lib/llm-wiki/wiki
sudo /usr/local/sbin/llm-wiki-admin wikisvc reindex --full
sudo /usr/local/sbin/llm-wiki-admin wikisvc lint
```

Переносите существующую вики — **не запускайте `init`**. Идите в
[8.3 Перенос данных](#83-перенос-данных), затем возвращайтесь к токенам.

`llm-wiki-admin` — хелпер: читает `/etc/llm-wiki/service.env`, переходит в рабочий
каталог и запускает CLI от нужного пользователя. Везде ниже он используется
именно так.

## 1.3. Токены

```sh
# рабочий токен агента
sudo /usr/local/sbin/llm-wiki-admin wikisvc token create \
  --name wikiagent --person wikiagent --kind agent --role writer --clearance restricted
sudoedit /etc/llm-wiki/agent.env       # впишите токен после WIKIAGENT_TOKEN=

# служебный токен веб-интерфейса
sudo /usr/local/sbin/llm-wiki-admin wikisvc token create \
  --name wiki-ui --kind agent --role reader --clearance public
sudoedit /etc/llm-wiki/ui-session.token   # только значение, без KEY= и кавычек
```

**Токен показывается один раз.** В базе только хеш. Потеряли — отзывайте
(`token revoke NAME`) и выпускайте новый с **другим** `name`, сохранив тот же
`person`. Повторно выдать тот же `name` нельзя.

Токену `wiki-ui` доступен ровно один вызов — выпуск человеческой сессии.
Даже `/whoami` и MCP для него закрыты; права `reader/public` ограничивают ущерб,
если охрана путей когда-нибудь ошибётся.

`person` — это идентичность человека, а не имя токена. У всех токенов одного
человека он должен совпадать: автор предложения не может принять его другим
токеном, и сравнивается именно `person`.

## 1.4. Вход через Authentik

Сначала настройте IdP, потом запускайте `wiki-ui`: без issuer, client id
и непустых файлов секретов он откажется стартовать. Настроенный, но временно
недоступный IdP запуску не мешает.

**В Authentik:** Application `wiki` с confidential OAuth2/OIDC Provider —
authorization code, PKCE S256, RSA signing key (RS256), issuer mode per-provider.

**Subject** — стабильный непрозрачный, например user UUID. **Не `user_username`**:
переименование логина не должно превращать человека в другого человека.
После запуска subject mode не меняют.

**Redirect URI** — точный browser-origin:
`https://wiki.example.org/auth/callback` для TLS-прокси или
`http://127.0.0.1:8789/auth/callback` для SSH-туннеля.

**Scopes** `openid`, `profile`, `email`, `groups` плюс включённый
**Include claims in id_token**. Для `groups` создайте property mapping:

```python
return {"groups": [group.name for group in request.user.groups.all()]}
```

и выберите его в провайдере. Без mapping все получат `reader/public`.

**Сопоставление групп** — `/etc/llm-wiki/roles.yaml` (root:llm-wiki, 0640, вне вики):

```yaml
default: {role: reader, clearance: public}
groups:
  wiki-readers:   {role: reader,   clearance: internal}
  wiki-writers:   {role: writer,   clearance: internal}
  wiki-reviewers: {role: reviewer, clearance: restricted}
  wiki-admins:    {role: admin,    clearance: restricted}
```

При нескольких группах берутся максимальные роль и допуск; неизвестные группы
не дают ничего. Изменение карты требует перезапуска `wikisvc` и нового входа —
уже выданные сессии живут со своими правами до отзыва или конца TTL.

```sh
sudoedit /etc/llm-wiki/ui.env           # issuer, client id, redirect, cookie
sudoedit /etc/llm-wiki/ui-oidc.secret   # только client secret
sudoedit /etc/llm-wiki/roles.yaml
timedatectl                             # нужно System clock synchronized: yes
```

**Время обязательно синхронизировано** (`chronyd` или `systemd-timesyncd`) — и для
окон самолечения, и для проверки `exp`/`iat`/`nbf` в токенах OIDC: будущий `iat`/`nbf`
допускается не более чем на 60 секунд, истёкший `exp` отвергается.

Issuer обязан быть HTTPS. Для частного CA укажите в `ui.env`
`SSL_CERT_FILE=/etc/llm-wiki/idp-ca.pem` — PEM-bundle системных корней **и** вашего CA,
читаемый пользователем `llm-ui`. Проверка TLS отключению не подлежит;
`WIKI_UI_OIDC_INSECURE_HTTP=1` допустим только на локальном стенде с loopback-IdP.

## 1.5. Локальная модель

GGUF и `llama-server` ставятся **отдельно** под оборудование сервера: Nix bundle
вики не содержит ни CUDA, ни модели. Сначала убедитесь, что выбранный бинарник
вообще запускается на этой машине и умеет structured JSON для вашего файла.

```sh
sudo cp /path/to/model.gguf /srv/llm-wiki/models/
sudo chown llm-model:llm-model /srv/llm-wiki/models/model.gguf
sudo chmod 0640 /srv/llm-wiki/models/model.gguf
sudoedit /etc/llm-wiki/llama.env        # LLAMA_SERVER_BIN и LLAMA_ARG_MODEL — абсолютные пути
sudoedit /etc/llm-wiki/wikiagent.yaml
```

Для split-GGUF скопируйте все части и укажите первую. Бинарник и модель должны
быть доступны пользователю `llm-model`; `/home` и `/root` от службы скрыты.
Установщик добавляет `llm-model` в существующие группы `video`/`render`.
Если `llama-server` тоже из Nix — держите его в постоянном profile или другом
GC root, а библиотеки драйвера должны быть доступны с **хоста**.

**Два файла обязаны согласоваться:**

| `llama.env` | `wikiagent.yaml` | начальное значение |
|---|---|---|
| `LLAMA_ARG_ALIAS` | `models.*.model` | `wiki-gemma-31b` |
| `LLAMA_ARG_HOST` / `PORT` | `models.*.base_url` | `127.0.0.1:18089` → `.../v1` |
| `LLAMA_ARG_CTX_SIZE` | `models.*.context` | `16384` |
| `LLAMA_ARG_N_PARALLEL` | — | `1` |
| `LLAMA_ARG_N_GPU_LAYERS` | — | `auto` |

Alias и контекст должны совпадать, иначе агент не найдёт модель. 16K — стартовое
значение; его пригодность зависит от квантования, RAM/VRAM и GPU. Не хватает
памяти — уменьшайте контекст **в обоих файлах** и заодно
`limits.chapter_chunk_tokens` (для 16K это 4000). Несколько слотов без пересчёта
контекста на слот не включайте.

## 1.6. Запуск и проверка

```sh
sudo systemctl enable --now llm-wiki-model wikisvc
sudo journalctl -u llm-wiki-model -n 80 --no-pager
curl --fail http://127.0.0.1:18089/health
curl --fail http://127.0.0.1:8787/api/v1/health

# дождаться загрузки модели, проверить токен, alias и генерацию JSON
sudo /usr/local/sbin/llm-wiki-admin check --dependencies-only --wait 600 --model

sudo systemctl enable --now wikiagent wiki-ui
curl --fail http://127.0.0.1:8789/healthz
sudo /usr/local/sbin/llm-wiki-admin check --model
```

`wikiagent` сам ждёт API вики и зарегистрированную модель до десяти минут, затем
systemd повторяет попытку. Проверка `--model` делает по одному короткому запросу
к каждой уникальной настроенной модели, предложений и задач не создаёт.
Она проверяет **совместимость протокола, а не качество решений модели.**

Качество проверяется сценариями:

```sh
sudo /usr/local/sbin/llm-wiki-admin wikiagent eval \
  --scenarios "$PWD/tests/scenarios" --out /var/lib/llm-wiki/agent/eval.json
```

Каталог должен быть доступен пользователю `llm-wiki` — из закрытого home
скопируйте `tests/scenarios/` в `/var/lib/llm-wiki/agent/scenarios/`.
В комплекте 12 сценариев; порог полного допуска — не менее 30 сценариев
и не менее 90% правильных результатов.

## 1.7. Доступ

Со своего компьютера достаточно SSH-туннеля:

```sh
ssh -N -L 8789:127.0.0.1:8789 user@wiki-host
```

и **http://127.0.0.1:8789** в браузере. Для туннеля задайте именно этот origin
в redirect URI и оставьте `WIKI_UI_COOKIE_SECURE=1`: loopback в современном
браузере считается доверенным контекстом.

Все обращения к вики и агенту идут через Go-прокси внутри `wiki-ui`.
Сессионный токен живёт только в HttpOnly/Secure/SameSite=Lax cookie —
JavaScript его не видит. У службы `llm-ui` нет доступа ни к файлам вики,
ни к рабочему токену агента. Статика и шрифты встроены в бинарник: ни Node.js,
ни внешние CDN для работы не нужны.

**Для общего доступа** поставьте TLS reverse proxy перед `127.0.0.1:8789`:
проксируйте `/` целиком, сохраняйте `Cookie` и `Origin`, **выключите буферизацию**
(иначе сломается потоковый чат), таймаут — не ниже таймаута модели. Загружаете
книги — поднимите лимит тела до настроенного размера.

Swagger остаётся на `http://127.0.0.1:8787/docs` и `:8788/docs` — для доступа
добавьте отдельные SSH forwards.

Исходящий интернет нужен только `wiki-ui` для обращения к Authentik. Ядру
интернет не нужен вовсе, агент работает с локальной моделью.

> **Анонимный доступ.** Комплект включает `ANONYMOUS_ACCESS=1`: запрос к API/MCP
> без заголовка `Authorization` получает `writer/internal` с `kind=agent`.
> **Такой API нельзя публиковать в интернет** — любой добравшийся сможет создавать
> предложения. Ограничьте сеть и поставьте лимит **по IP на прокси**: все анонимные
> клиенты делят одну идентичность и общий пул предложений. Решения, `restricted`
> и `wikiagent` им недоступны; неверный переданный токен всегда даёт 401.

## 1.8. Резервное копирование

GitHub хранит код. `state.db`, worktrees, библиотеку, сессии и `agent.env`
не хранит никто. Установщик кладёт `llm-wiki-backup.service`, `.timer`
и `/etc/llm-wiki/backup.env`, но **таймер включает человек**.

По умолчанию: ежедневно в **23:00 по местному времени сервера**, каталог
`/var/backups/llm-wiki`, срок хранения 14 дней.

Задание останавливает `wiki-ui`, `wikiagent`, `wikisvc` и архивирует `wiki/`
(с `.git`), `state/`, `agent/` и `/etc/llm-wiki` (включая `agent.env`).
Индекс не входит — он пересобирается. Модель останавливать не нужно.
**Горячая копия не годится:** SQLite и worktrees дадут рваный архив, который
выглядит целым до дня восстановления. На время копирования завершите и отдельные
пишущие процессы CLI/MCP, а службы вручную не поднимайте.

Каталог — root `0700`, архивы — root `0600`, после создания применяется
`restorecon`. Архив получает имя `data-<дата-UTC>-<суффикс>.tar.gz` только после
успешного `tar`; при ошибке прежние копии не удаляются.

Зарезервируйте окно **23:00–01:00** — оно не пересекается с поставляемым окном
самолечения 01:00–06:00. `Persistent=true` догоняет пропущенный запуск, поэтому
после простоя копирование может начаться сразу, вне обычного окна: включайте
таймер в период обслуживания.

`ExecStopPost` ставит запуск служб в очередь через `systemctl --no-block start`
даже после ошибки, поэтому упавший архив не оставит систему выключенной.
Но постановка в очередь — ещё не запуск: проверяйте и результат задания,
и состояние служб.

### Обязательная проверка восстановления

**Непроверенная копия копией не считается.** Проверяйте после первой копии
и регулярно после обновлений. `llm-wiki-admin` здесь **не используется**: он
читает рабочий `service.env` и тронул бы живую вику.

```sh
sudo sh -eu <<'RESTORE'
test ! -e /tmp/restore-test
test ! -L /tmp/restore-test
install -d -m 0700 /tmp/restore-test
trap 'rm -rf -- /tmp/restore-test' EXIT
tar --no-same-owner -C /tmp/restore-test \
  -xzf '/var/backups/llm-wiki/data-<дата-UTC>-<суффикс>.tar.gz'
install -d -m 0700 /tmp/restore-test/index

for cmd in repair-worktrees 'reindex --full' lint; do
  env WIKI_ROOT=/tmp/restore-test/var/lib/llm-wiki/wiki \
      STATE_DIR=/tmp/restore-test/var/lib/llm-wiki/state \
      INDEX_DIR=/tmp/restore-test/index \
      /opt/llm-wiki/current/bin/wikisvc $cmd
done
RESTORE
```

Все три пути задаются явно, потому что `Settings` читает только окружение.
Ни одна команда проверки не указывает на рабочий `/var/lib/llm-wiki`. Каталог
`0700` и удаляется в любом случае: внутри `agent.env` и внутренние материалы.

После успешной проверки:

```sh
sudo systemctl enable --now llm-wiki-backup.timer
systemctl list-timers llm-wiki-backup.timer
```

## 1.9. Включение самолечения и аудита документации

Оба выключены в комплекте намеренно. Порядок включения — по пунктам, без пропусков:

1. Выполните первую операцию руками: человек проверил и принял хотя бы одно предложение.
2. `llm-wiki-admin check --model` проходит.
3. `timedatectl` — часовой пояс сервера тот, который вы ожидаете: окна используют
   местное время.
4. Резервное копирование настроено и **проверено**, окна не пересекаются с окном
   бэкапа, включая остановку и запуск служб.
5. Только теперь `heal.enabled: true` (и/или `docs_audit.enabled: true`)
   в `/etc/llm-wiki/wikiagent.yaml`, затем `sudo systemctl restart wikiagent`.
6. Через сутки откройте `GET /api/v1/findings/stats` человеческим токеном.
   Если по виду находок отклонено больше половины решённых, ответ содержит
   `recommendation: "Поднять порог уверенности"`. Много ложных срабатываний
   означает, что `confidence_threshold` **занижен** — его повышает человек
   в `wikiagent.yaml`. Система свой порог не меняет никогда.

# 2. Все параметры настройки

Все env-файлы — синтаксис systemd `EnvironmentFile`: `KEY=value` или
`KEY="value with spaces"`. Без `export`, без `$VAR`, без обратных кавычек
и команд. Их читают и systemd, и CLI-хелпер.

## 2.1. `/etc/llm-wiki/service.env` — ядро

Пути. Меняете их за пределы `/var/lib/llm-wiki` — обновите также
`ReadWritePaths`/`RequiresMountsFor` через `systemctl edit`.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `WIKI_ROOT` | — | репозиторий контента. **Обязателен** |

# 3. Веб-интерфейс: что делает человек

Откройте адрес UI — вход перенаправит в Authentik. Входа по токену в интерфейсе
нет: только OIDC. Светлая и тёмная темы, мобильная навигация, поиск по
<kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>K</kbd>. Выход отзывает сессию и чистит кэш.

Чтение вики, ручное редактирование, ревью, источники, граф и экспорт инструкций
работают независимо от готовности модели. Без модели недоступен только чат.

## 3.1. Экраны

| Экран | Для чего |
|---|---|
| **Пространство** | что требует внимания: очередь на проверку, незавершённые задачи, брошенные знания, план изменений |
| **Знания** | поиск и фильтры по типу, названию и содержанию; переход к странице |
| **Страница** | текст, frontmatter, связи, кто и когда подтвердил, история |
| **Чат** | диалог с агентом знаний; из разговора получается план изменений |
| **Проверка** | очередь человека: предложения и находки, решение с комментарием |
| **Предложение** | diff, влияние, допущения, блокирующие вопросы, принять или отклонить |
| **Политики** | собрать инструкцию по профилю: бюджет, режим проверяемых правил, что попало в контекст и чего не хватило |
| **Источники** | загрузка книг и документов, оглавление, текст, запуск разбора |
| **Граф** | связи между правилами, системами, паттернами и источниками |
| **Задачи** | фоновые задачи: разбор книги, самолечение, сверка документации; отмена и продолжение |
| **Настройки** | кто вы, роль, допуск, тип участника, адрес вики, версии |

## 3.2. Правило родилось в разговоре

1. **Чат** → выберите профиль; при необходимости привяжите диалог к странице,
   правилу или предложению.
2. Напишите как есть: «мы используем FastAPI и только async-код».
3. Агент вернёт **план**: тезисы, diff страницы, влияние на профили, допущения
   и блокирующие вопросы. Ответ в том же диалоге уточняет черновик.
   Вложением можно передать ранее загруженное сырьё.
4. Проверьте план и примите предложение в **Проверке**. Сам агент этого
   сделать не может ни одним путём.
5. Правило от агента всегда приходит инертным: `candidate`, `should`, `priority 3`.
   Чтобы оно попало в инструкции, человек повышает его отдельным действием,
   а для `must` обязан указать владельца и источник решения.

Если план затрагивает действующее `must`, интерфейс просит дополнительное
подтверждение.

## 3.3. Правило родилось из книги

1. **Источники** → загрузите файл, укажите категорию и зачем он команде.
   Книги идут в библиотеку (до 200 МиБ), сырьё по категориям — в Git (до 25 МиБ).
2. Запустите разбор. PDF с текстовым слоем, EPUB, DOCX, MD/TXT разбираются
   порциями в ограниченном подпроцессе. Скан без текстового слоя даёт
   `E_NO_TEXT_LAYER` — OCR в системе нет.
3. Нет оглавления — задайте его руками и продолжите задачу.
4. Агент читает по главам и готовит кандидатов. **Полный текст книги в вики
   не попадает** — остаются библиография, выжимка и короткие проверяемые цитаты.
5. Кандидаты ждут человека и в инструкции не входят, пока их не повысят.

Цитаты вида `[@src-id стр. 12 "до 30 слов"]` проверяются по кэшу текста.
Выдуманная цитата отвергается.

## 3.4. Проверка: очередь человека

На одном экране предложения и находки. Решение сохраняется вместе
с комментарием.

- **Принять** — слияние, подтверждение затронутых активных правил и решения
  идут **одним** коммитом; при ошибке операция откатывается целиком.
- **Отклонить** — с причиной.
- **Отклонить находку** — причина **обязательна** и держится до изменения текста правила.
- **Откатить** принятое предложение вместе с решениями. Если последующие коммиты
  меняли те же страницы — `409 E_REVERT_CONFLICT`, разбирайтесь вручную.

Автор не принимает своё предложение: сравнивается `person`, а не имя токена.
Решения доступны только участнику с `kind=human`.

## 3.5. Политики: что увидит агент

**Политики** → профиль, бюджет токенов, режим машинно проверяемых правил
(сохранять обязательные / скрывать проверяемые / включать все). Справа — что
попало в контекст, сколько занято из бюджета и какие правила исключены и почему.

Это тот же результат, который получает агент через `get_policies`, и то же,
что `wk policy sync` впишет в `AGENTS.md`.

# 4. Работа в своём проекте: `wk`

`wk` — статический Go-бинарник, который живёт в репозитории **проекта**, а не вики.
Это единственный инструмент, который запускают разработчик и его агент.

## 4.1. Создать проект

```sh
nix run .#wk -- init --dir ../orders-platform \
  --url http://127.0.0.1:8787 --profile go-service
cd ../orders-platform
nix develop path:. -c wk doctor --json
```

`init` раскладывает скелет документации, блок политик, манифест
`.wiki-project.yaml`, `git init`, `flake.nix`, `.gitignore`, хуки и навыки агента.
`--template ID` берёт готовый шаблон из вики — тогда профиль и scopes приходят
из него, иначе `--profile` обязателен. `--scopes lang:go,app:orders` задаёт области
вручную. Имя проекта по умолчанию — имя каталога, иначе `--project`.

Сразу после `init` файлы ещё не в Git, поэтому `nix develop path:.` — Nix увидит их
без staging. `wk` делает только `git init` и `git status`: что добавлять и коммитить,
решает человек. Коммитов и Git-hooks он не создаёт.

`--url` или `WIKI_URL` нужны только для `init`; дальше всё берётся из манифеста.

| Вариант | Что делает |
|---|---|
| `init` | полный комплект в пустом каталоге |
| `init --existing` | в непустой каталог: `docs/`, `AGENTS.md`, манифест и отсутствующие хуки с навыками |
| `init --force --existing` | перезаписать конфликтующие файлы проекта; существующие хуки и навыки сохраняются |
| `init --offline --template ID` | из проверенного локального кэша; блок политик помечается как ещё не загруженный |

Кэш используется **только** с `--offline`. Вика недоступна или шаблон в ней сломан —
`init` останавливается до записи любого файла и печатает код ошибки сервера.
Молчаливого перехода на старую локальную копию нет: проект, созданный не из того
шаблона, который вы просили, хуже отсутствующего проекта.

Повторный `init` с валидным манифестом и без `--force` доставляет **только**
отсутствующие хуки и навыки, не трогая остальное и сохраняя mtime. Пути и конфликты
проверяются до записи, манифест пишется последним.

## 4.2. Команды

| Команда | Назначение |
|---|---|
| `doctor` | по порядку `ok`/`warn`/`fail`: манифест, health, whoami, профиль, scopes, политики, MCP, агент, docs, навыки, git |
| `component add NAME [--lang LANG-id] [--kind svc\|lib] [--with-ai]` | компонент из локального `_template`: draft, ID, владелец, строка в INDEX |
| `docs check [--docs DIR] [--code DIR] [--strict] [--no-registry]` | проверка документации и генерация реестра ID |
| `docs upgrade` | удалить старый `docs/_meta/check.py` |
| `check [--strict]` | документация **и** актуальность блока политик |
| `policy sync` | вписать актуальный блок политик, атомарно |
| `policy check` | сравнить версию блока с серверной |
| `policy search QUERY` / `policy show RULE-ID` | читать правила вики из терминала |
| `template list` / `template show ID` | реестр шаблонов и канонический YAML с digest |
| `propose --file PAGE.md [--title T] [--kind manual]` | черновик → страница → валидация → на ревью |
| `hook check\|guard-block\|guard-paths\|policy-stale` | обработать событие харнесса из stdin |

Все обычные команды понимают `--json`: один документ на stdout, диагностика
на stderr. Значение `WIKI_TOKEN` вычищается из любого вывода.

Коды выхода: `0` — успех, `1` — ошибка, `2` — неизвестная команда или аргументы,
`3` — нет `docs/` или манифеста. `doctor` даёт `0` при `ok`/`warn` и `1` при любом
`fail`; отсутствующие MCP и агент — предупреждения.

Чего у `wk` нет и не будет: команд принятия, повышения, снятия и откатa правил.

## 4.3. Повседневный цикл

```sh
wk policy sync          # политики изменились — подтянуть блок
wk check                # перед коммитом
wk check --strict       # в CI: предупреждения тоже ошибки
wk propose --file docs/...  # поспорить с правилом, а не править блок руками
```

Блок политик **генерируется** — править его руками бессмысленно: следующий
`sync` перезапишет, а `check` до этого будет падать. Нужно изменить правило —
`wk propose`, и дальше решает человек в вики.

## 4.4. Манифест `.wiki-project.yaml`

```yaml
version: 1
project: orders-platform
wiki:
  url: http://127.0.0.1:8787
  profile: go-service
  scopes: [lang:go, app:orders]
policy_blocks:
  - file: AGENTS.md
    profile: go-service
    scopes: []            # пусто — берутся из профиля
    budget_tokens: null   # null — значение профиля
    enforced: keep_must   # keep_must | all | none
template:
  id: ""
  digest: ""
docs:
  root: docs
```

`project` — `[a-z0-9][a-z0-9-]{0,63}`, `version` строго `1`. `wiki.url` — origin
http/https без завершающего слэша, пути, query, fragment и userinfo.
`docs.root` и `policy_blocks[].file` — относительные пути внутри проекта,
без `..`, `.git`, абсолютных путей и симлинков.

Запрещены: неизвестные поля на любом уровне, повторные ключи, несколько
YAML-документов, aliases, merge keys и любые ключи, содержащие `token`,
`secret`, `password` без учёта регистра. Манифест — не место для секретов.

## 4.5. Навыки агента

Названная процедура, которую человек вызывает одной командой: `/имя`
в claude-code, `$имя` в codex. `wk init` раскладывает их в `.claude/skills/`
и `.agents/skills/`.

| Навык | Когда вызывать |
|---|---|
| `policy-sync` | перед началом работы: подтянуть правила компании и проверить проект |
| `doc-card` | завести или изменить факт в `docs/` — карточку или строку таблицы с ID |
| `implement-planned` | реализовать факты со статусом `planned` и поставить маркеры `doc:<ID>` |
| `propose-rule` | в политиках пробел — предложить правило в общую вику |

Каждый навык заканчивается `wk check --strict`: процедура, оставившая проект
непроверенным, свою работу не сделала.

## 4.6. Хуки агента

Правила в `AGENTS.md` — просьба, которую модель может проигнорировать. Хук —
команда харнесса, и он либо проходит, либо блокирует.

| Хук | Событие | Что делает |
|---|---|---|
| `hook check` | `Stop` | проверки не прошли — ход не завершается, причина уходит агенту |
| `hook guard-block` | `PreToolUse` | правка внутри блока политик — отказ |
| `hook guard-paths` | `PreToolUse` | правка проверяющего инструмента, конфигурации хуков или манифеста — отказ |
| `hook policy-stale` | `SessionStart` | блок устарел — одна строка-напоминание, не блокирует |

Защищены четыре пути: `docs/_meta/check.py`, `.claude/settings.json`,
`.codex/hooks.json`, `.wiki-project.yaml`. Последние два — потому что иначе защита
снимает себя сама: в одном живут хуки, из другого они берут, что защищать.
Личные настройки `.claude/settings.local.json` не защищаются.

Офлайн гейт на остановке пропускает ход намеренно: ход, который агент не может
ни завершить, ни починить, — тупик, а не защита. Непробиваемость в этом случае
обеспечивает CI тем же `wk check --strict`.

**Чего хуки не закрывают.** Матчер ловит инструменты записи файлов, то есть те,
что передают путь в `tool_input.file_path`. Правка того же файла через shell —
`sed -i`, `cat > file` — мимо них проходит. Поэтому `wk check --strict`
обязательным шагом в CI нужен **всегда**, а не только там, где хуков нет:
это единственная проверка, которую агент со своей машины обойти не может.
Хуки дают быструю обратную связь, непробиваемость даёт CI.

# 5. Как правила получает агент

Через MCP или HTTP API. Порядок работы один и тот же:

1. `get_instructions` — **всегда первым**;
2. `get_policies(profile)` — компактный свод действующих правил под задачу;
3. `get_rule(id)` — подробности, исключения и связи того правила, которое мешает;
4. `rules_related`, `graph_impact` — что ещё затронуто.

В инструкцию входят только активные `must` и `should` с пересекающимися scopes
или `*`. Все `must` сохраняются даже сверх бюджета — тогда в ответе
`over_budget: true`. Машинно проверяемые `should` по умолчанию опускаются
(их нарушение поймает CI), а `must` помечаются проверяющим инструментом;
`enforced=all|none|keep_must` меняет это поведение.

**Профили инструментов.** `coding` — 13 инструментов: правила, поиск, чтение,
предложения. `full` — все 20, плюс книги, источники и заметки.
Для stdio: `wikisvc mcp --profile coding` (по умолчанию `full`).
Для HTTP: `MCP_HTTP_ENABLED=True` в процессе `wikisvc serve`, профиль — `MCP_PROFILE`
(по умолчанию `coding`), путь — `MCP_PROFILE`/`MCP_HTTP_PATH`.

HTTP-транспорт использует общий Runtime без повторной индексации. При выключенном
анонимном доступе каждый запрос требует `Authorization: Bearer <token>`;
`WIKI_TOKEN` работает только для stdio. Неверный переданный токен отвергается всегда.

Операций принятия, повышения, снятия и откатa у агента нет **ни в одном
транспорте**. Это не настройка.

# 6. Роли и права

Роли: `reader` → `writer` → `reviewer` → `admin`.
Допуск: `public` → `internal` → `restricted`.

| Может | reader | writer | reviewer | admin |
|---|---|---|---|---|
| читать страницы своего допуска | да | да | да | да |
| поиск, граф, контекст, политики | да | да | да | да |
| создавать и отправлять предложения | — | да | да | да |
| загружать сырьё и книги (нужен `restricted`) | — | да | да | да |
| принимать, отклонять, откатывать | — | — | **только человек** | **только человек** |
| повышать и снимать правила | — | — | **только человек** | **только человек** |
| отклонять находки | — | — | **только человек** | **только человек** |
| `GET /admin/audit` | — | — | — | да (+`restricted`) |

Решения требуют `kind=human`. Агент с ролью `reviewer` их не получит:
проверяется тип участника, а не роль.

**Недоступная страница даёт `404`, а не `403`,** и исчезает из поиска, контекста,
графа, истории, индекса и предложений. Разница между «нет» и «не для тебя» сама
является утечкой.

Авторизация предшествует чтению тела запроса. JSON и Markdown ограничены 1 МиБ.
Неавторизованные запросы не заполняют аудит.

# 7. Полный список возможностей

**Хранение и поиск**

- Markdown в отдельном Git-репозитории; записи через worktrees и атомарные коммиты
- типы страниц, связи, теги, scopes и профили — схемой управляет администратор
- поиск BM25 с русскими и английскими словоформами, стоп-словами и синонимами;
  `1С` и `1C` нормализуются одинаково; AND с откатом на OR
- `deprecated` по умолчанию скрыты
- граф связей: `rules/related`, `graph/impact/{id}`, `proposals/{pid}/impact`
- счётчики доставок, открытий и нарушений по каждому правилу

**Правила и инструкции**

- тип `rule` с уровнем, жизненным циклом, областями, владельцем и источником
- компиляция инструкции по профилю с бюджетом токенов и версией-хешем
- экспорт блока в файл проекта; `wikisvc policies export` / `check`
- защищённые поля: `lifecycle`, `level`, `priority`, `owner`, `verified_*`
- `wikisvc scopes add` — новая область, коммитом

**Предложения и решения**

- цикл create → put/patch → validate → submit → diff/impact → accept/reject
- `kind`: `manual`, `chat`, `book`, `heal`
- слияние, подтверждение затронутых правил и решения — одним коммитом,
  с полным откатом при ошибке
- `revert` принятого предложения вместе с решениями
- запрет саморевью по стабильной идентичности
- предупреждение при понижении уровня доступа страницы
- TTL неактивных предложений

**Работа с моделью**

- чат с планировщиком, потоковые события, привязка к странице или правилу
- план: тезисы, diff, влияние, допущения, блокирующие вопросы
- разбор книг по главам с контрольными точками и ручным оглавлением
- самолечение: поиск противоречий внутри вики, находки и предложения
- сверка `docs/` проекта с политиками (`docs_audit`)
- бюджеты на проход и на сутки, кэш по хешам, порог уверенности
- `wikiagent eval` — сценарная проверка модели

**Источники**

- библиотека книг до 200 МиБ, сырьё по категориям до 25 МиБ
- PDF с текстовым слоем, EPUB, DOCX, MD/TXT; извлечение в ограниченном подпроцессе
- оглавление, чтение по главам и страницам, продолжение по курсору
- проверяемые цитаты с локаторами; дедупликация по SHA-256
- транслитерация русских имён файлов с сохранением оригинала

**Очередь человека**

- `/inbox`, `/findings`, `/findings/stats`
- отклонение находки с обязательной причиной
- рекомендация поднять порог при избытке ложных срабатываний

**Интеграции**

- HTTP API `/api/v1`, Swagger `/docs`, схема `/openapi.json`
- MCP: stdio и Streamable HTTP, профили `coding` и `full`
- `wk` в репозитории проекта: документация, политики, предложения, хуки, навыки
- шаблоны проектов из вики — только данные, без исполняемых полей

**Эксплуатация**

- Nix-сборка, четыре systemd-службы, отдельные пользователи, loopback
- вход через OIDC с картой групп, сессии в HttpOnly-cookie
- аварийный human-токен с ограниченным сроком
- лимит запросов на токен, детектор секретов, пометка `untrusted_external`
- резервное копирование таймером с обязательной проверкой восстановления
- `repair-worktrees` после переноса, `reindex --full`, `lint`, миграции state.db

**Намеренно отсутствует:** OCR сканов, эмбеддинги, графовая БД, мультиузловое
развёртывание, предложения из находок `docs_audit`, клиентский путь к `wikiagent`
без человеческой сессии.

# 8. Эксплуатация

## 8.1. Ежедневно

```sh
sudo systemctl status wikisvc wikiagent wiki-ui llm-wiki-model
sudo journalctl -u wikisvc -u wikiagent -u wiki-ui -u llm-wiki-model -f
sudo /usr/local/sbin/llm-wiki-admin check            # без обращения к модели
sudo /usr/local/sbin/llm-wiki-admin check --model    # плюс короткий запрос к модели
```

Диагностика входа проверяет по локальной базе карту ролей и служебный токен UI:
отсутствие, отзыв, истечение срока или лишние полномочия — `fail`. Печатает
сопоставленные группы. Недоступность discovery и несинхронизированное время — `warn`.

## 8.2. Обновление и откат

Сначала собрать новое, пока работает старое. Потом остановить и сделать копию.

```sh
git pull --ff-only
nix --extra-experimental-features 'nix-command flakes' \
  build .#deployment --out-link result-deployment

sudo systemctl stop llm-wiki-backup.timer
# идёт копирование — дождитесь его конца
sudo systemctl stop wiki-ui wikiagent wikisvc llm-wiki-model

sudo install -d -m 0700 /var/backups/llm-wiki
command -v restorecon >/dev/null && sudo restorecon /var/backups/llm-wiki
sudo sh -eu -c 'umask 077; tar -C / \
  -czf "/var/backups/llm-wiki/pre-upgrade-$(date -u +%Y%m%dT%H%M%SZ).tar.gz" \
  var/lib/llm-wiki/wiki var/lib/llm-wiki/state var/lib/llm-wiki/agent etc/llm-wiki'
# проверьте эту копию по инструкции восстановления из 1.8

sudo ./result-deployment/bin/llm-wiki-install
sudo /usr/local/sbin/llm-wiki-admin wikisvc schema upgrade
sudo /usr/local/sbin/llm-wiki-admin wikisvc reindex --full
sudo /usr/local/sbin/llm-wiki-admin wikisvc lint

sudo systemctl start llm-wiki-model wikisvc wikiagent wiki-ui
sudo /usr/local/sbin/llm-wiki-admin check --model
sudo systemctl start llm-wiki-backup.timer    # если был включён
```

**`backup.service` для копии перед обновлением не годится:** его `ExecStopPost`
вернёт службы в работу посреди обслуживания.

Откат — предыдущий bundle лежит в `/opt/llm-wiki/previous`. Миграции `state.db`
применяются при старте и сохраняют данные, но откат на версию без миграции
требует восстановления из копии.

Установщик **сохраняет** существующие конфиги: новые параметры из
`deploy/linux/service.env` и `ui.env` добавляйте вручную и перезапускайте службу.

## 8.3. Перенос данных

GitHub содержит **код**. Данные переносятся отдельно: весь `wiki/` включая `.git`,
весь `STATE_DIR`, весь `WIKIAGENT_STATE_DIR`, конфиги и `agent.env`. Индекс —
пересоздаётся.

До копирования остановите `wiki-ui`, `wikiagent`, `wikisvc` и прочие пишущие
клиенты CLI/MCP. На старой машине до конца переноса запись не возобновляйте.

Для развёрнутой установки берите проверенный архив из раздела резервного
копирования. Для dev-структуры, где вика лежит рядом с кодом
(`WIKI_ROOT=../wiki`, состояние в `.dev/` репозитория кода):

```sh
umask 077
tar -czf wiki-data.tar.gz wiki llm-wiki/.dev/state
# плюс фактический state_dir агента целиком, обычно llm-wiki/.dev/agent
```

На новой машине распакуйте в закрытый каталог и разложите:
`wiki/` → `/var/lib/llm-wiki/wiki`, state → `/var/lib/llm-wiki/state`,
каталог агента → `/var/lib/llm-wiki/agent`. Копируйте вместе со скрытыми файлами
(`cp -a SOURCE/. DEST/`), только в пустые каталоги, не смешивая с другой установкой.

```sh
sudo chown -R llm-wiki:llm-wiki /var/lib/llm-wiki
command -v restorecon >/dev/null && sudo restorecon -RF /var/lib/llm-wiki /etc/llm-wiki
sudo /usr/local/sbin/llm-wiki-admin wikisvc repair-worktrees
sudo /usr/local/sbin/llm-wiki-admin wikisvc schema upgrade
sudo /usr/local/sbin/llm-wiki-admin wikisvc reindex --full
sudo /usr/local/sbin/llm-wiki-admin wikisvc lint
```

`repair-worktrees` исправляет абсолютные связи Git после смены путей и отказывается
продолжать при недостающем worktree. Открытые предложения сохраняются.
Обычный `git clone` контента не переносит ни `state.db`, ни worktrees, ни книги,
ни сессии, ни токены.

Конфиги проверьте отдельно: старые абсолютные пути и прежнее имя модели
не подойдут. `agent.env` нужен с токеном, который соответствует скопированной
`state.db`; нет такого — выпустите новый агентский токен. GGUF копируется отдельно.
Архив содержит внутренние материалы и `agent.env` — храните с правами рабочих данных.

Не запускайте старую и новую копии агента одновременно на одном рабочем наборе.

## 8.4. Обновление существующей вики до слоя политик

```sh
wikisvc schema upgrade                  # добавить схему слоя политик
wikisvc migrate-rules --dry-run         # отчёт без изменения страниц
wikisvc migrate-rules                   # готовит предложение, человек принимает
wikisvc schema upgrade --refresh-instructions   # заменить стандартные инструкции шаблоном v2
wikisvc reindex --full
wikisvc lint
```

Без `--refresh-instructions` существующие `AGENTS`/workflows не заменяются —
перенесите свои дополнения до замены.

Старые страницы `convention`/`stack`/`security`/`testing` становятся кандидатами
`rule`, ссылки переписываются внутри предложения. Старые токены получают
`kind=agent`: для решений перевыпустите человеческий токен с
`--kind human --person <sub>`. Для прежних предложений без `person` идентичностью
автора считается старое имя токена — сохраните его при перевыпуске.

В старом `.gitignore` контента должны быть `.obsidian/`, `inbox/*`,
`!inbox/.gitkeep`.

## 8.5. Аварийный доступ

Выпустите токен **до** аварии. `--person` обязан точно совпадать с вашим `sub`
из Authentik (виден как `person` в `/api/v1/whoami`) — иначе вы получите вторую
идентичность и обойдёте запрет саморевью.

```sh
sudo /usr/local/sbin/llm-wiki-admin wikisvc token create \
  --name breakglass --person '<ваш sub>' --kind human --role admin \
  --clearance restricted --expires-at '<ISO-8601 с часовым поясом>'
```

Храните вне сервера, как пароль от сейфа; раз в квартал проверяйте
`GET /api/v1/whoami`. В аварии работайте напрямую с API через локальный доступ
или SSH-туннель — входа по токену в UI нет.

```sh
curl --fail -H "Authorization: Bearer $BREAKGLASS_TOKEN" \
  "http://127.0.0.1:8787/api/v1/proposals/$PID"
# изучите diff/impact и notes.accept_body, сохраните проверенный как accept.json
curl --fail -X POST -H "Authorization: Bearer $BREAKGLASS_TOKEN" \
  -H 'Content-Type: application/json' --data-binary @accept.json \
  "http://127.0.0.1:8787/api/v1/proposals/$PID/accept"
sudo /usr/local/sbin/llm-wiki-admin wikisvc token revoke breakglass
```

**Вслепую не принимайте.** Штатные проверки человеческого решения и запрет
саморевью в аварийном доступе действуют полностью. После использования выпустите
новый токен с другим `name` и тем же `person`.

# 9. Что делать, когда не работает

| Симптом | Куда смотреть |
|---|---|
| `401` | токен: выдан, не отозван, не истёк, заголовок дошёл |
| `403` | роль, допуск и `kind`. Решения требуют `kind=human` |
| `404` на существующей странице | это не ошибка: страница выше вашего допуска |
| `429 E_RATE_LIMIT` | `RATE_LIMIT_PER_MIN`, лимит на имя токена |
| ошибка alias модели | сравните `/v1/models` с `models.*.model` в YAML |
| GPU OOM | журнал `llm-wiki-model`; уменьшайте контекст **в двух файлах** и `chapter_chunk_tokens` |
| `E_NO_TEXT_LAYER` | скан без текстового слоя, OCR в системе нет |
| `E_QUOTE_NOT_FOUND` | цитата не найдена в источнике или странице |
| `E_REVERT_CONFLICT` | те же страницы менялись после принятия — разбирайте вручную |
| `E_SELF_REVIEW` | принять своё предложение нельзя: нужен другой человек |
| `E_SECRET_DETECTED` | в тексте опознан секрет — уберите его |
| `409` на чтении источника | кэш извлечения ещё не готов |
| `422 E_TEMPLATE_INVALID` | шаблон **сломан**: смотрите причину в ответе, `wikisvc lint` или журнал `wikisvc` |
| `404 E_TEMPLATE_UNKNOWN` | шаблона с таким ID в вике нет — проверьте `wk template list` |
| `503` при входе | IdP недоступен; существующие сессии живут TTL |
| `wikiagent` не стартует | ждёт API и модель до 10 минут, затем systemd повторяет |
| AVC при SELinux | `sudo ausearch -m AVC -ts recent` |

**Вход не работает.** Сравните redirect URI **побайтно** с настройкой провайдера.
Затем issuer, client id, secret, NTP, CA. После входа нет прав — проверьте scope
mapping групп и **Include claims in id_token**; роль и допуск видны в настройках UI.
После выхода локальная сессия отзывается даже при отказе IdP, и ошибка страницы
end-session доступ не возвращает.

**Блок политик «повреждён или неоднозначен».** В файле больше одного маркера
`<!-- wikisvc:begin` или блок обрезан. `wk` намеренно не трогает такой файл —
почините разметку руками, затем `wk policy sync`.

**Шаблон проекта не загружается.** Различайте два ответа: `404 E_TEMPLATE_UNKNOWN`
означает, что шаблона с таким ID в вике нет, а `422 E_TEMPLATE_INVALID` — что он
есть, но сломан и отправлен в карантин. Битый шаблон **не** мешает работе сервиса:
остальные шаблоны выдаются, политики компилируются, вика работает. Причина
карантина видна в ответе, в `GET /api/v1/schema`, в `wikisvc lint` и одной строкой
WARNING в журнале при старте. Исправьте файл в `schema/project-templates/`
и выполните `reindex` — шаблон выйдет из карантина без перезапуска служб.

Основная схема — типы страниц, связи, scopes, профили — наоборот, останавливает
старт при любой ошибке. Без неё сервис не может ответить на свой главный вопрос,
и отказ стартовать честнее выдачи политик по половине схемы.

**`wk` говорит «симлинки запрещены».** Внутри проекта симлинки не поддерживаются
ни в одном пути, который трогает `wk`.

**Хук ничего не блокирует.** Блокирует только код выхода 2. Если в группу `Stop`
подставить `wk check --strict` вместо `wk hook check`, гейт станет украшением:
прямая команда возвращает 1 при ошибках и 3 без сети.

## Границы, которые не настраиваются

Это инварианты, а не параметры. Их нельзя ослабить конфигурацией — попытка
поднять потолок приводит к отказу при старте.

1. Решения принимает человек: `accept`, `promote`, `deprecate`, `revert`,
   `dismiss` требуют `kind=human`.
2. Автор не принимает своё предложение.
3. Новое правило от агента всегда инертно: `candidate`, `should`, `priority 3`.
4. Ядро детерминировано: `wikisvc` не вызывает модель и не делает исходящих запросов.
5. Одна машина: блокировка записи — локальный файл.
6. Внешние данные недоверенные: ответы модели, книги, загруженные файлы
   и проектная документация проверяются, помечаются `untrusted_external`
   и не исполняются. Инструкции внутри них игнорируются.
7. Потолок анонимного доступа задан кодом: всегда `kind=agent`, роль не выше
   `writer`, допуск не выше `internal`.
8. `wikiagent` не принимает анонимные вызовы, и допуск вызывающего обязан быть
   не ниже допуска рабочего токена агента.
9. Политика попадает в проект только блоком с версией; пересказ запрещён.
10. Проверяющий код не лежит в проверяемом репозитории.
