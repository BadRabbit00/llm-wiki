# ТЗ v2: свод правил для агентов, умный ввод и самолечение (репозиторий `llm-wiki` / `wikisvc`)

Документ для агента-разработчика. Он заменяет первую версию ТЗ. База (хранилище в git, предложения, поиск, граф, авторизация, MCP) уже есть и хорошо проверена. Здесь описано, что изменить и добавить, чтобы из «вики знаний» получился **свод правил для агентов, которые пишут код**, причём так, чтобы правила не приходилось писать руками.

## 0. Правила работы

- Идти по этапам из раздела 16. Не начинать следующий этап, пока не проходят тесты предыдущего.
- Если чего-то не хватает в документе, выбрать самое простое решение, записать его в `docs/decisions.md` и продолжать.
- Сохранить текущее качество: `mypy --strict`, `ruff check`, `ruff format --check`, покрытие ядра не ниже 85 %, все существующие тесты безопасности зелёные. Нестабильные тесты (например, property-тест на `\r\n`) чинить, а не игнорировать.
- Любое изменение схемы `state.db` делать миграцией (`ALTER TABLE ... ADD COLUMN`, если колонки нет). Индекс можно пересобирать.
- Любое изменение репозитория контента идёт через существующие механизмы (предложения и операции ревьюера), без обходных записей в git.
- В `wikisvc` не добавлять вызовы LLM. Всё, что требует модель, живёт в отдельном компоненте `wikiagent` (раздел 12).
- Обновить `README.md`, `docs/decisions.md`, `docs/progress.md`, шаблон `AGENTS.md` и сценарии.

## 1. Цель, сценарии, приоритеты

Компания автоматизирует бизнес, приложения пишут агенты. Руководство требует закрепить свод правил: стек, стиль кода, логирование, версионирование, безопасность. Идея продукта: **короткие тезисы идут в системную инструкцию агента, подробности агент достаёт из вики по id**. Так экономится контекст.

**Главный критерий качества: простота добавления правил.** Писать сотню markdown-файлов вручную слишком долго. Путь от мысли до действующего правила должен занимать два действия человека: сформулировать фразу в чате и нажать «Применить».

Сценарии, которые обязаны работать (в порядке приоритета):

1. **Умный ввод.** Человек пишет в чат: «Мы используем FastAPI и только async код». Модель разбирает фразу на утверждения, проверяет по вики, что уже есть, находит дубликаты, уточнения и конфликты, составляет набор правок с объяснениями и показывает его на подтверждение. После подтверждения всё записывается куда надо, включая связи. Человеку задаются только блокирующие вопросы. (Раздел 7.)
2. **Самолечение.** Когда модель простаивает, а в вики накопились правки, она перепроверяет правила и связи, находит несостыковки (противоречия, дубликаты, потерянные связи, устаревшее) и выносит их на ревью вместе с готовыми исправлениями. Сама ничего не меняет. (Раздел 8.)
3. **Агент получает инструкцию.** Для проекта на Python и FastAPI сервис собирает компактный список тезисов. Правила, которые к проекту не относятся (например, про .NET), в список не попадают вообще. К каждому тезису добавлена ссылка `→ rule-id`. Подробности агент берёт через `get_rule(id)` вместе со связанными правилами. (Разделы 4 и 6.)
4. **Правила из книг, статей и документов.** Человек загружает книгу или вставляет текст. Та же логика, что в сценарии 1, применяется к каждой главе. Результаты это кандидаты, они безопасны и в инструкцию не попадают, пока человек их не повысит. (Раздел 10.)
5. **Требования руководства.** Обязательные правила (`must`) всегда имеют владельца и источник решения.

Принципы:

- Источник правды остаются markdown-файлы в git. Сервис детерминированный и без LLM. Модели это клиенты сервиса.
- Агент никогда не принимает, не повышает и не снимает правила. Решение всегда принимает человек, но оно должно стоить одного нажатия.
- Правило, которое проверяет машина (линтер, CI), надёжнее правила, которое помнит модель. Поэтому у правила есть поле «чем проверяется».
- Тезис должен быть понятен без перехода по ссылке. Ссылка нужна для примеров, исключений и спорных случаев.
- Связи важнее текста: агент, который открыл правило, должен увидеть его исключения, уточнения и конфликты.

## 3. Тип `rule`

### 3.1. Файл правила

```markdown
---
id: rule-logging-json-lines
type: rule
title: Логи в формате JSON, одно событие в строке
summary: Пиши логи только в JSON, одно событие на строку; секреты и персональные данные не логируй.
status: verified
sensitivity: internal
category: logging
level: must            # must | should | idea
lifecycle: active      # candidate | active | deprecated
applies_to: [lang:python, lang:dotnet]   # или ["*"]
priority: 4            # 1..5, по умолчанию 3
origin: management     # management | team | book | article | chat | code
owner: role-platform-lead               # обязателен для level: must
enforced_by: [tool:ruff, ci:log-lint]   # или [] / [none]
aliases: [логирование, logging, структурные логи]
sources: [src-directive-2026-09-logging]
tags: [engineering]
relations:
  refines: [rule-observability-basics]
---

## Правило
Подробная формулировка: что именно делать и что нельзя.

## Обоснование
Почему это правило существует.

## Примеры
Так:
```python
logger.info("invoice_approved", extra={"invoice_id": 42})
```
Не так:
```python
print(f"approved {invoice}")
```

## Исключения
Когда правило не применяется. (Раздел необязательный.)
```

### 3.2. Поля и проверки

- **`summary` у `rule` и есть тезис.** Ограничение 20..160 символов, одна строка, повелительное наклонение. Его показывает инструкция. Длину задаёт поле `summary_max: 160` в YAML типа (добавить в `PageType`). Отдельное поле `thesis` не заводить.
- Обязательные разделы: «Правило», «Обоснование», «Примеры». Раздел «Исключения» необязателен.
- Дополнительные поля типа `rule` (в `schema/page-types/rule.yaml`):

| Поле | Тип | Обязательно | Значения |
|---|---|---|---|
| `category` | строка | да | `code-style`, `architecture`, `logging`, `errors`, `security`, `testing`, `stack`, `git`, `build-ci`, `docs`, `process` (список редактируется в YAML) |
| `level` | строка | да | `must`, `should`, `idea` |
| `lifecycle` | строка | да | `candidate`, `active`, `deprecated` |
| `applies_to` | список строк | да, минимум 1 | `*` или значения из `schema/scopes.yaml` |
| `priority` | число | нет | 1..5, по умолчанию 3 |
| `origin` | строка | да | `management`, `team`, `book`, `article`, `chat`, `code` |
| `owner` | строка | для `must` | `role-…` или id человека |
| `enforced_by` | список строк | нет | `tool:<имя>` или `ci:<имя>`, либо `none` |
| `deprecated_reason` | строка | при `lifecycle: deprecated` | до 200 символов |

- **Расширить `ExtraField`** (`domain/registry.py`, `domain/validate.py`): добавить `type: str | int | list` (по умолчанию `str`), для списков `item_enum`, `item_pattern`, `min_items`, `max_items`, для строк `max_length`, для чисел `min` и `max`. Сейчас проверки рассчитаны только на строки, это место переписать аккуратно и покрыть тестами.
- Связи уровня, жизненного цикла и подтверждения:
  - `lifecycle: active` требует `verified_by` (правило хотя бы раз подтверждал человек). Иначе `E_RULE_ACTIVE_NOT_VERIFIED`.
  - `lifecycle: candidate` всегда с `status: draft` и уровнем `idea` или `should`.
  - `level: must` без `owner` даёт `E_MUST_NEEDS_OWNER`.
  - `origin: book|article` требует хотя бы один источник в `sources` и хотя бы одну цитату со страницей в теле (`W_NO_CITATION`, предупреждение).
  - `lifecycle: deprecated` требует `deprecated_reason`.
- **Защита от самовольного включения.** Запись через предложение не может менять `lifecycle`, `level`, `priority`, `owner`, `verified_*`: для существующей страницы сервис сохраняет прежние значения этих полей, для новой ставит `lifecycle: candidate`, `status: draft`. Патч-операция `set_field` по этим полям возвращает `E_FIELD_PROTECTED`. Менять их можно только при `accept` с повышением (раздел 9.2) и операциями ревьюера (раздел 9.1).
- **Правка активного правила.** При `accept` сервис автоматически подтверждает (`status: verified`, `verified_by`, `verified_at`) активные правила, изменённые в предложении: сам `accept` человеком это и есть подтверждение изменения. Новые и изменённые кандидаты остаются `draft`.

### 3.3. Области применения и профили

`schema/scopes.yaml`: контролируемый словарь значений `applies_to`:

```yaml
- "lang:python"
- "lang:dotnet"
- "lang:typescript"
- "framework:fastapi"
- "app:telegram-bot"
- "app:service"
- "app:cli"
```

Неизвестное значение даёт `E_SCOPE_UNKNOWN`. Правило действует, если в `applies_to` есть `*` или оно пересекается со списком областей проекта (логика «любое из»). Условий «И» нет: сочетания выражаются более узкими значениями.

`schema/profiles/*.yaml`: профиль проекта.

```yaml
id: python-fastapi
title: Python-сервис на FastAPI
scopes: ["lang:python", "framework:fastapi", "app:service"]
budget_tokens: 2000
```

**Новые области создаёт человек или планировщик через предложение в `scopes.yaml`?** Нет: `scopes.yaml` и `profiles/` лежат вне `wiki/` и через предложения не меняются (как теги). Если планировщик не находит подходящую область, он задаёт вопрос человеку, а человек добавляет область командой `wikisvc scopes add <значение>` (запись в `schema/scopes.yaml`, коммит, пересборка индекса). Чат показывает эту команду в подсказке.

### 3.4. Связи (`schema/relations.yaml`)

Добавить:

| rel | обратная | откуда → куда | примечание |
|---|---|---|---|
| `refines` | `refined_by` | rule → rule | уточняет, не заменяет |
| `conflicts_with` | `conflicts_with` (симметрична) | rule → rule | фиксирует найденное противоречие |

Остальные (`supersedes`, `depends_on`, `related`, `part_of`) использовать как есть для `rule`. `governed_by` остаётся, но не обязательна.

### 3.5. Тип `source`

Добавить дополнительные поля: `kind` (обязательно: `book`, `article`, `directive`, `chat`, `interview`, `doc`, `code`), необязательные строки `author`, `year`, `edition`, `url`. Поля `raw_path`, `raw_sha256` остаются обязательными (для чата это сохранённая расшифровка в `raw/transcripts`). Источник типа `directive` это документ, письмо или протокол руководства, на него ссылаются обязательные правила.

### 3.6. Удаляемые типы

Удалить `convention.yaml`, `stack.yaml`, `security.yaml`, `testing.yaml` из шаблона и реестра. Тест `test_all_paths` ждёт сейчас 16 типов, новое число: 13 (16 − 4 + 1). Обновить фикстуры и тесты. Если в рабочей вики уже есть страницы удалённых типов, дать команду `wikisvc migrate-rules --dry-run`, которая превращает их в кандидатов `rule` (тезис это первая фраза раздела «Правило», обрезанная до 160 символов, `origin: team`, `level: idea`) и печатает отчёт. Автоматически ничего не публиковать, результат оформить как предложение.

## 4. Компилятор инструкции

### 4.1. Алгоритм

Вход: профиль (`profile`) или явный список областей (`scopes`), `budget_tokens` (по умолчанию из профиля), `enforced` (`keep_must` по умолчанию, `all`, `none`).

1. Кандидаты: страницы `rule` с `lifecycle: active` и `level` в (`must`, `should`), чьё `applies_to` подходит под области проекта.
2. Правила с непустым `enforced_by` (не `none`): при `enforced=keep_must` остаются только `must` и помечаются «проверяется: …», а `should` исключаются, потому что такие нарушения поймает CI.
3. Порядок: `must` раньше `should`, внутри уровня по `priority` (больше раньше), затем по порядку категорий (настраивается), затем по `id`. Порядок детерминирован.
4. Бюджет: оценка токенов строки `ceil(len(строка) / chars_per_token)`, где `CHARS_PER_TOKEN` настраивается (по умолчанию 2.5, консервативно для русского). Сначала добавляются все `must`, затем `should`, пока есть место. Если `must` не влезают, собрать всё равно и вернуть `over_budget: true`.
5. `idea` в инструкцию не попадают никогда. Они доступны через поиск и `get_rule`.

### 4.2. Формат вывода

```markdown
## Правила компании (профиль python-fastapi, версия 7f3a9c1d, около 1240 токенов)

Обязательные:
- [MUST] Пиши логи только в JSON, одно событие на строку; секреты не логируй. (проверяется: ruff) → rule-logging-json-lines
- [MUST] Новые зависимости добавляй только после решения в ADR. → rule-stack-new-deps

Желательные:
- [SHOULD] Комментируй «почему», а не «что»; у публичных функций пиши docstring. → rule-comments-why

Подробности: вызови get_rule(id). Открывай правило, когда применяешь его впервые в задаче,
сомневаешься в исключениях или пишешь примеры.
```

Заголовок и подвал лежат в шаблоне `schema/policy-template.md` и редактируются без правки кода.

JSON-ответ:

```json
{
  "profile": "python-fastapi", "scopes": ["lang:python", "framework:fastapi", "app:service"],
  "budget_tokens": 2000, "used_tokens": 1240, "version": "7f3a9c1d", "over_budget": false,
  "markdown": "...",
  "included": [{"id": "rule-logging-json-lines", "level": "must", "category": "logging", "tokens": 38}],
  "omitted": [{"id": "rule-x", "reason": "budget"}, {"id": "rule-y", "reason": "enforced"}],
  "omitted_counts": {"scope": 12, "lifecycle": 5, "level": 30}
}
```

`version` это первые 8 символов SHA-256 от отсортированных id, `content_hash` включённых правил и параметров запроса.

### 4.3. Интерфейсы

- `GET /api/v1/policies/compile?profile=&scopes=&budget_tokens=&enforced=&explain=` (роль `reader`). При `explain=true` в `omitted` попадают все исключённые с причинами.
- `GET /api/v1/profiles`, `GET /api/v1/scopes`.
- MCP-инструмент `get_policies(profile | scopes, budget_tokens)`. MCP-инструмент `get_rule(id)`: как `get_page`, плюс блок «Связанные» (раздел 6.3), засчитывается как «открытие правила».
- CLI `wikisvc policies export --profile python-fastapi --out ../myapp/AGENTS.md`: записывает компактный блок между маркерами `<!-- wikisvc:begin version=… -->` и `<!-- wikisvc:end -->`, остальное содержимое файла не трогает. `wikisvc policies check --profile … --file …` сообщает, устарел ли блок (сравнивает `version`).
- Кэш результата компиляции по (профиль, бюджет, `enforced`, хеш индекса), сбрасывается при любом изменении индекса.

### 4.4. Учёт использования

Таблица в `state.db`: `rule_usage(rule_id, day, delivered, opened, violations)`.

- `delivered` растёт для каждого правила в ответе `compile`.
- `opened` растёт, когда токен с `kind: agent` (раздел 11) запрашивает страницу `rule-*` через `get_rule` или `get_page`.
- `violations` увеличивает `POST /api/v1/rules/violations` (обзор соблюдения, второй этап).
- `GET /api/v1/rules/stats?days=30` (роль `reviewer`) возвращает по каждому правилу три счётчика и признаки `never_opened`, `often_violated`. Цель: находить тезисы, которые агенты игнорируют или нарушают, и переписывать или убирать их.

## 5. Поиск и подбор связанного

### 5.1. Доработка поиска

Проверка показала: запросы «как писать логи в python», «что логировать» и «logging python» возвращают пусто, хотя правило есть. Причины: строгое «И» по всем словам, нет стоп-слов, производные слова («логировать», «логирование») не склеиваются.

Изменения в `index/normalize.py` и `index/search.py`:

1. Список стоп-слов (русские и английские служебные слова), которые отбрасываются из запроса. Список лежит в файле данных, не в коде.
2. Если поиск «И» даёт меньше `k/2` результатов, выполнить мягкий поиск «любое из слов» с ранжированием BM25 и пометить такие результаты `via: "partial"`.
3. Поля `aliases` участвуют в поиске. Для правил требовать хотя бы 2 алиаса (русский и английский вариант): `W_FEW_ALIASES`, предупреждение.
4. Необязательный файл `schema/synonyms.yaml` (группы синонимов), подмешиваемых в запрос и индекс.
5. Параметр `lifecycle=` (список) в `GET /search` и `GET /pages`: по умолчанию поиск не показывает `deprecated`; планировщик и лекарь запрашивают все жизненные циклы.

### 5.2. Подбор связанного для утверждения

`GET /api/v1/rules/related?q=<утверждение>&scopes=<области>&limit=10` (роль `reader`). Возвращает для утверждения на естественном языке:

- найденные правила **всех** жизненных циклов (активные, кандидаты, снятые) с полями `id`, тезис, `level`, `lifecycle`, `applies_to`, `score_rank`, `via`;
- для каждого найденного правила его соседей по связям `refines`, `refined_by`, `conflicts_with`, `supersedes`, `superseded_by`, `depends_on` (только id и тезис);
- страницы других типов (`pattern`, `playbook`, `adr`, `app`), найденные по тому же запросу и по `impact_terms` (необязательный параметр: слова, присутствие которых означает затронутость, например «requests, sync»).

Это единая точка, через которую планировщик (раздел 7) и лекарь (раздел 8) находят связанное. Допуск токена соблюдается так же, как в поиске.

Приёмка: запрос «только async код» находит правило «Для HTTP-запросов используй requests» (проверено на фикстурах), выдаёт его соседей и страницу паттерна с синхронным примером.

## 6. Граф: решение и использование

### 6.1. Решение: графовую базу данных не вводим

Идея отдельной графовой базы понятна: связи важны, и их нельзя терять. Но для этой задачи она не нужна сейчас, и вот почему:

1. **Источник правды git.** Граф это производный индекс (как сейчас). Внешняя графовая БД это вторая копия, которую нужно согласовывать с git при каждом `accept`, `revert`, пересборке и восстановлении после сбоя. Мы только что закрывали такие сбои для одного индекса, а с двумя копиями их станет больше.
2. **Масштаб.** Свод правил это сотни или тысячи узлов. Свой сервис ради этого означает отдельные доступ, бэкап и поверхность атаки.
3. **Замер.** Я измерил обход графа на SQLite (синтетический граф со «хабами», плотность связей выше, чем бывает в реальной вики правил):

| Граф | Текущая реализация (`index/graph.py`) | Тот же SQLite, обход волнами по индексам |
|---|---|---|
| 2 000 страниц, 10 000 связей | 120 мс (глубина 2), 361 мс (глубина 3), 1007 мс (хаб, глубина 3) | 3 мс, 9 мс (хаб, глубина 3), 18 мс (хаб, глубина 5) |
| 20 000 страниц, 100 000 связей | 3,4 с (глубина 2), 51 с (глубина 3), 84 с (хаб, глубина 3) | 51 мс, 141 мс (хаб, глубина 3), 364 мс (хаб, глубина 5) |

Медленно не хранилище, а форма запроса: промежуточная таблица `arcs` без индекса просматривается целиком на каждом шаге рекурсии. Переписанный обход быстрее в 100–250 раз. Это единственное, что нужно исправить.

### 6.2. Что сделать с обходом

- Выделить интерфейс `GraphStore` (`typing.Protocol`) с методами `neighbors`, `path`, `impact`, `subgraph(ids, rels, depth)`, `export`. Реализация `SqliteGraphStore`. Так хранилище можно будет заменить позже без изменения остального кода.
- Обход волнами: на каждой волне один запрос `SELECT dst FROM edges WHERE src IN (...) UNION SELECT src FROM edges WHERE dst IN (...)` пачками по 400 id, множество посещённых в Python. Добавить индекс `edges(dst, rel)` и `edges(src, rel)`, если плана запроса без них недостаточно.
- Допуск применять на каждой волне: страницы выше допуска токена не раскрываются, их рёбра и сами узлы не возвращаются и не участвуют в обходе дальше (как сейчас через `visible_edges`). Скрытие должно остаться побитово эквивалентным (тест ниже).
- Тесты: результаты `neighbors`, `path`, `export` на фикстурах совпадают с прежней реализацией (эталонные файлы); тесты изоляции по допуску на всех поверхностях остаются зелёными; скрипт `scripts/benchmark_graph.py` воспроизводит таблицу из 6.1, мягкий порог в тесте: 2 000 страниц, 10 000 связей, глубина 3 не дольше 100 мс.

### 6.3. Как граф сохраняет важное вместо графовой БД

- **`get_rule(id)` возвращает связанные правила.** Кроме самого правила, блок «Связанные» (по `refines`/`refined_by`, `conflicts_with`, `supersedes`/`superseded_by`, `depends_on`/`required_by`): id, тезис, `level`, `lifecycle`, не больше 600 токенов. Агент, открывший правило, видит исключения, уточнения и конфликты, а не только само правило.
- **Анализ влияния.** `GET /api/v1/graph/impact/{id}?depth=2&rels=`: все страницы, которые ссылаются на эту или зависят от неё (обратные рёбра, транзитивно), с типом связи и расстоянием. Используется планировщиком, лекарем и ревьюером.
- **Влияние предложения.** `GET /api/v1/proposals/{pid}/impact`: для всех изменённых страниц предложения кто затронут (обратные связи глубины 2 по `refines`, `conflicts_with`, `supersedes`, `depends_on`, `governed_by`, `implements`) и какие активные правила пересекаются с ними по областям. Показывать ревьюеру рядом с diff.
- **Целостность при правках.** Новая проверка `W_DEPENDS_ON_DEPRECATED` (активное правило зависит от снятого, уточняет его или ссылается на него). `deprecate` и `supersedes` возвращают список зависимых страниц.
- **Области как узлы графа.** В `GET /graph/export?include_scopes=true` области применения отдаются узлами `scope:lang:python` с рёбрами `applies_to` (для интерфейса). В индексе такие рёбра не хранятся, строятся при экспорте.

### 6.4. Граф в конвейерах

Планировщик (раздел 7) и лекарь (раздел 8) опираются на `rules/related` и `impact`, а не на собственный обход: так логика поиска связей в одном месте.

### 6.5. Когда вернуться к вопросу графовой БД

Пересматривать решение, если выполняется хотя бы одно условие после оптимизации:

1. Больше 100 000 связей или 20 000 правил и p95 обхода глубины 3 дольше 500 мс.
2. Самолечению нужны шаблонные запросы по путям (поиск подграфов) или графовые алгоритмы (сообщества, центральность), которые дорого писать на SQL.
3. Появляется несколько экземпляров сервиса с общими данными.

Тогда подключаем графовую БД через интерфейс `GraphStore` как производный индекс. Git остаётся источником правды, а индекс пересобирается из файлов.

## 7. Умный ввод: из фразы в набор правок

Это главная функция. Она живёт в `wikiagent` (раздел 12) и использует API `wikisvc`.

### 7.1. Пример

Человек пишет: «Мы используем FastAPI и только async код». В вики уже есть активное правило «Для HTTP-запросов используй requests» (`lang:python`, `should`) и страница паттерна с синхронной функцией-обработчиком FastAPI.

Ожидаемый результат (набросок карточек плана, которые видит человек):

1. Создать правило `rule-stack-fastapi` («Пиши веб-сервисы на Python на FastAPI», категория `stack`, `should`, области `lang:python`, `framework:fastapi`).
2. Создать правило `rule-async-only` («Пиши код сервисов только асинхронным: `async def` и неблокирующие вызовы», категория `code-style`, `should`, `lang:python`, `framework:fastapi`).
3. **Вопрос:** правило `rule-http-requests-sync` противоречит новому. Заменить его (создам `rule-http-httpx-async` и сниму старое), развести области или не добавлять новое?
4. Отметить страницу `pat-fastapi-sync-endpoint` как затронутую (её пример синхронный): правка не делается автоматически, только заметка человеку.
5. Допущения: применяю к `lang:python`, уровень `should` (укажите `must`, если это требование руководства).

После ответа и нажатия «Применить» правила записаны, связи расставлены, профиль `python-fastapi` получил новую версию инструкции.

### 7.2. Конвейер (модуль `wikiagent.planner`)

Один движок `plan_changes(claims, context)` обслуживает чат, задачи по книгам и самолечение (где применимо). Шаги:

1. **Разбор.** Модель роли `planner` извлекает из сообщения утверждения: `[{text, kind, category, scopes_guess, level_guess, impact_terms}]`. `kind`: `rule` (требование или решение) или `not_rule` (описание бизнес-процесса и прочее, не про правила: сообщить человеку, что такие знания относятся ко второму этапу). Утверждение вида «мы используем X» превращается в правило категории `stack`. Не больше 10 утверждений за раз; длиннее разбирается пачками.
2. **Подбор связанного.** Для каждого утверждения вызов `GET /rules/related` (все жизненные циклы, с соседями) и `GET /graph/impact/{id}` для найденных.
3. **Классификация.** Модель по жёсткой JSON-схеме относит утверждение к каждой найденной странице: `new`, `duplicate_of(id)`, `refines(id)`, `extends_scope(id)`, `conflicts_with(id)`, `supersedes(id)`, `affects(id, how)` с `confidence` и цитатой-доказательством из найденной страницы. Цитата проверяется на вхождение в текст страницы, иначе вывод отбрасывается и запрашивается повторно (до 3 раз).
4. **План правок.** Детерминированно из классификации: `create_rule`, `patch_rule` (операции `PATCH`), `supersede_rule` (новое правило со связью `supersedes`, старое попадает в предложение заметкой и снимается при `accept`), `add_relation`, `flag_page` (затронутая страница: заметка человеку, не правится), `noop_duplicate` (уже покрыто). Каждый пункт с причиной, уверенностью и предварительным diff.
5. **Вопросы.** Только блокирующие, не больше 3 за ход: конфликт с активным или `must`-правилом (кто побеждает), сигнал, что это требование руководства (нужен владелец), неоднозначная область. Всё остальное решается по умолчанию и выносится в план как **допущение**.
6. **Предложение.** `create_proposal` (статус `draft`, `kind: chat`), `put_page` и `patch_page` для каждого пункта, `validate_proposal`; ошибки валидации чинятся автоматически циклом не более 3 раз. Затем `PUT /proposals/{pid}/notes` с планом, вопросами, допущениями и влиянием (раздел 9.3), и ответ в чат.
7. **Подтверждение.** Человек нажимает «Применить». Интерфейс вызывает `POST /proposals/{pid}/accept` **человеческим токеном** с телом `promote` (раздел 9.2). Агент никогда не принимает и не повышает. «Поправить» означает новую реплику: планировщик обновляет то же предложение (шаги 3–6). «Отмена» делает `abandon`.
8. **Итог.** В чат приходит сообщение: что записано, какие профили изменились (с новой версией инструкции) и как экспортировать (`wikisvc policies export`). Для отката: «отменить» вызывает `revert` (раздел 9.4).

### 7.3. Значения по умолчанию (чтобы не задавать лишних вопросов)

- Уровень `should`. `must` предлагается, только если в формулировке есть сигнал («обязательно», «запрещено», «руководство требует»). Для `must` обязателен владелец: единственный вопрос «кто владелец?».
- `origin: team`, `sources`: страница-источник с расшифровкой чата (раздел 7.6).
- Области: из области сессии (профиль, выбранный в чате), иначе угадываются по формулировке (язык, фреймворк); если не определены, план ставит `*` и записывает это в допущения. Если нужной области нет в `scopes.yaml`, вопрос человеку с готовой командой `wikisvc scopes add …`.
- Тезис формулируется по правилам качества: повелительное наклонение, одно правило на одну строку, не больше 160 символов, самодостаточен без ссылки.
- Алиасы: минимум два (русский и английский).
- Примеры «так / не так» генерирует модель, в разделе «Примеры» остаётся пометка «примеры предложены моделью, проверьте».

### 7.4. Контракт ответа чата (для интерфейса)

Сообщение ассистента содержит блок `plan` (JSON) рядом с текстом:

```json
{
  "proposal": "p-20260930-01",
  "summary": "Создам 2 правила, найден 1 конфликт, затронута 1 страница",
  "items": [
    {"n": 1, "action": "create_rule", "target": "rule-stack-fastapi", "thesis": "…",
     "level": "should", "scopes": ["lang:python", "framework:fastapi"],
     "reason": "Утверждение о стеке, похожих правил нет", "confidence": 0.93},
    {"n": 4, "action": "flag_page", "target": "pat-fastapi-sync-endpoint",
     "reason": "Пример содержит синхронный обработчик"}
  ],
  "questions": [{"id": "q1", "text": "Правило rule-http-requests-sync противоречит новому. Что сделать?",
                 "options": ["Заменить новым", "Развести области", "Не добавлять новое"]}],
  "assumptions": ["Применяю к lang:python", "Уровень should"],
  "impact": {"profiles": ["python-fastapi"], "pages": ["pat-fastapi-sync-endpoint"]},
  "needs_double_confirm": false
}
```

Интерфейс рисует карточки пунктов, кнопки для вопросов и кнопки «Применить», «Поправить», «Отмена». Поле `needs_double_confirm` равно `true`, если набор затрагивает `must`-правила или больше 5 страниц: тогда интерфейс просит второе явное подтверждение.

### 7.5. Размер набора

Не больше 10 пунктов в предложении. Если утверждений больше, планировщик делит их по темам на несколько предложений и предупреждает об этом. Так ревью остаётся осмысленным, а не формальным.

### 7.6. Другие входы в тот же конвейер

- Вставленный текст (регламент, заметки, письмо): сохраняется как источник (`raw/transcripts/…`, `source` с `kind: doc` или `chat`), разбирается на утверждения и идёт тем же путём.
- Вложенный файл: сохраняется через `POST /raw` (книги в `library`), дальше раздел 10.
- Книга: обход по главам, результаты идут как кандидаты (раздел 10.3).
- Репозиторий кода (второй этап): правила извлекаются из конфигурации линтеров, CI, Dockerfile, настройки логирования; `origin: code`, `kind: code`.

Вся переписка сессии сохраняется в `raw/transcripts/<сессия>.md` при создании предложения, и правила ссылаются на страницу-источник с решением («решено в чате такого-то числа, автор такой-то»).

### 7.7. Оценка планировщика

- Сценарии-эталоны в `tests/scenarios/*.yaml` (вход, исходная вики, ожидаемые действия и вопросы). Минимум 12: новое без пересечений; дубликат; уточнение; расширение области; конфликт с `should`; конфликт с `must` (вопрос и владелец); затронутая страница паттерна; неоднозначная область; пачка из 5 правил; нерелевантное утверждение (`not_rule`); ответ на вопрос планировщика; «отмени».
- Команда `wikiagent eval --role planner --model <имя>` прогоняет сценарии и считает: долю верных действий, ложные конфликты, лишние вопросы, попытки запретных вызовов. Порог для боевого использования: не меньше 90 % верных действий на 30 сценариях, ноль попыток принять или повысить, в среднем не больше одного лишнего вопроса. Если малая локальная модель порог не проходит, роль `planner` переключается на сильную модель конфигурацией.

## 8. Самолечение

Вики находит свои несостыковки и предлагает исправления, а человек решает. Лекарь ничего не меняет сам.

### 8.1. Когда запускается

- **Простой.** Нет активных чат-сессий и задач дольше `idle_minutes` (по умолчанию 15), и есть страницы, изменённые с прошлого прохода.
- **Расписание.** Окна времени (`windows`, например `01:00-06:00`), плюс полный проход раз в `full_sweep_days` (по умолчанию 7).
- **Вручную.** `POST /jobs/heal` (область `changed` или `full`).
- **Чат важнее.** При входящем сообщении задача приостанавливается на ближайшей границе (после завершённой проверки пары) и возобновляется после. Модель достаётся чату.

### 8.2. Что проверяется

Детерминированные проверки (без модели, это lint `wikisvc`): битые ссылки, устаревшие зависимости, `W_RULE_CONFLICT`, `W_DEPENDS_ON_DEPRECATED`, `W_PROFILE_OVER_BUDGET`, слабый тезис и мало алиасов, правила без открытий и с частыми нарушениями (`rules/stats`), кандидаты, висящие дольше N дней.

Семантические проверки (модель):

1. Противоречия между правилами с пересекающимися областями.
2. Дубликаты и почти дубликаты: предложение слияния через `supersedes`.
3. Недостающие связи (уточняет, зависит): предложение `add_relation`.
4. Расхождение области и текста (в тексте «.NET», а `applies_to` только `lang:python`).
5. Устаревшее: правило опирается на снятое правило, отменённый ADR или противоречит более новому решению.
6. Качество тезиса (расплывчатый, два правила в одном, нет действия): предложение переформулировки.
7. Пробелы покрытия по категориям профиля (нет ни одного правила про обработку ошибок): подсказка, низкий приоритет.

### 8.3. Как не сравнивать всё со всем

- **Набор проверки:** страницы, изменённые или созданные с прошлого успешного прохода (по `content_hash`), плюс их окрестность по графу (глубина 1 по `refines`, `conflicts_with`, `supersedes`, `depends_on`, `refined_by`, `required_by`).
- **Пары-кандидаты** для каждой страницы набора: топ-`k_candidates` (по умолчанию 8) по поиску (BM25 по тезису и алиасам), соседи по графу и правила той же категории с пересекающимися областями. Не больше 20 пар на страницу.
- **Кэш пар:** таблица `pair_checks(a_id, a_hash, b_id, b_hash, verdict, confidence, checked_at)` в `agent.db`. Пара не проверяется повторно, пока не изменится хеш одной из страниц. Повторный прогон на неизменной вики не вызывает модель.
- **Бюджеты:** максимум вызовов модели за запуск и за сутки, максимум находок за запуск (по умолчанию 20). Порядок: конфликты с `must`, конфликты `should`, дубликаты, остальное.

### 8.4. Вердикт пары

Модель возвращает по JSON-схеме: `{relation: none|duplicate|refines|conflicts|scope_mismatch, confidence: 0..1, explanation, evidence: [{page, quote}], suggested_fix}`. Цитаты проверяются на вхождение в тексты страниц. Находка с выдуманной цитатой отбрасывается. Порог уверенности по умолчанию 0.7. Для конфликтов с `must` второе мнение даёт модель роли `reviewer`.

### 8.5. Находки (findings) и как они доходят до человека

Находки хранятся в `wikisvc` (`findings` в `state.db`), чтобы интерфейс работал с одним сервисом и очередью:

`findings(id, kind, severity, status, pages, summary, explanation, evidence, proposal_pid, run_id, fingerprint, created_at)`. `status`: `open`, `resolved`, `dismissed`. `fingerprint` это хеш от вида и хешей затронутых страниц (тот же вывод на тех же текстах не плодит новых записей).

- `POST /api/v1/findings` (роль `writer`, вставка или обновление по `fingerprint`).
- `GET /api/v1/findings?status=&kind=&severity=` (роль `reader`), `GET /api/v1/findings/stats` (принято и отклонено по видам).
- `POST /api/v1/findings/{id}/dismiss` с `{"reason": "..."}` (роль `reviewer`) и `.../reopen`.

Для находки с `suggested_fix` лекарь создаёт предложение (`kind: heal`, описание объясняет находку, цитаты обеих страниц, затронутые профили) и прикрепляет его `proposal_pid`. Предложение отправляется на ревью (`submit`). Принятие предложения переводит находку в `resolved`, отклонение переводит её в `dismissed` с обязательной причиной. Отклонённая находка не всплывает снова, пока не изменится одна из страниц. `GET /inbox` показывает число открытых находок.

### 8.6. Чего лекарь не делает

Не принимает предложения, не повышает и не снимает правила, не меняет `lifecycle`, `level`, `priority`, `owner`, не пишет напрямую в репозиторий контента. Его единственный результат: находки и предложения на ревью.

### 8.7. Настройки и метрики

`wikiagent.yaml`: `heal: {enabled, idle_minutes, windows, max_findings_per_run, max_model_calls_per_day, confidence_threshold, full_sweep_days, k_candidates}`. Если доля отклонённых находок по виду выше 50 %, панель показывает рекомендацию поднять порог. Автоматическая подстройка порога не делается.

### 8.8. Приёмка

Фикстурная вики с 40 правилами и 5 заложенными проблемами (конфликт, дубль, недостающая связь, несоответствие области тексту, зависимость от снятого правила). Заглушка модели отдаёт заготовленные вердикты. Проверяется:

- найдены все 5 проблем, у каждой есть предложение с исправлением;
- повторный запуск без изменений не вызывает модель (счётчик вызовов равен нулю);
- изменение одной страницы приводит к проверке только её пар;
- отклонённая находка не всплывает повторно, а после изменения страницы появляется снова;
- находка с выдуманной цитатой отбрасывается;
- входящее сообщение чата приостанавливает задачу и она возобновляется после ответа;
- лекарь не вызывает ни одного эндпоинта принятия или повышения (тест перехватывает все вызовы).

## 9. Предложения, подтверждение, откат, кандидаты

### 9.1. Кандидаты и триаж

Кандидаты безопасны: в инструкцию попадают только `active`. Поэтому пачку кандидатов из книги можно принять одним предложением, а разбирать по одному уже после слияния.

Операции ревьюера (прямой коммит, как `verify`; реализовать рядом с `services/review.py`):

- `POST /api/v1/rules/{id}/promote` с `{"level": "must|should", "priority": 1..5, "applies_to": [...], "owner": "...", "enforced_by": [...]}`: полная валидация, `lifecycle: active`, `status: verified`, `verified_by`, `verified_at`. Для `must` требует `owner`. Отказывает при ошибках `E_*`. Возвращает предупреждения о пересечении с действующими правилами.
- `POST /api/v1/rules/{id}/deprecate` с `{"reason": "..."}`: `lifecycle: deprecated`, `deprecated_reason`. Страница остаётся в вики, чтобы планировщик не предлагал ту же идею снова. Ответ перечисляет зависимые страницы.
- `GET /api/v1/rules?category=&level=&lifecycle=&applies_to=&origin=&source=&q=&sort=&limit=&cursor=`: список для таблицы (id, тезис, категория, уровень, жизненный цикл, области, происхождение, источник, `enforced_by`, счётчики использования).
- `GET /api/v1/inbox` (роль `reviewer`): одним запросом число предложений на ревью, необработанных источников, кандидатов на разбор (по источникам), открытых находок, незавершённых задач `wikiagent`, предупреждений lint по группам.
- `POST /api/v1/rules/violations` (роль `writer`): `{"items":[{"rule_id","note","ref"}]}`, увеличивает `violations` (обзор соблюдения, второй этап).

### 9.2. Подтверждение одним действием: `accept` с повышением

`POST /api/v1/proposals/{pid}/accept` принимает необязательное тело:

```json
{"promote": [{"id": "rule-async-only", "level": "should", "priority": 3,
              "applies_to": ["lang:python", "framework:fastapi"], "enforced_by": []}],
 "deprecate": [{"id": "rule-http-requests-sync", "reason": "Заменено rule-http-httpx-async"}]}
```

- Выполняется атомарно под блокировкой записи: слияние, автоматическое подтверждение изменённых активных правил (раздел 3.2), применение `promote` и `deprecate`, валидация, финальные коммиты. При любой ошибке всё откатывается (`merge --abort` или возврат к исходному коммиту), предложение остаётся в прежнем статусе.
- **Ограничение безопасности:** `promote` и `deprecate` допускаются только для страниц `rule`, которые есть в самом предложении. Произвольные правила повысить или снять нельзя.
- Право: только `reviewer` и выше, автор и редакторы по `person` (раздел 11) принимать не могут.
- **Принятие из `draft`.** Разрешено принимать предложение в статусе `draft`, если его автор имеет токен `kind: agent`: сервис делает неявный `submit` в той же операции при полной валидации. Это нужно, чтобы «Применить» в чате было одним действием. Для предложений с человеческим автором порядок прежний (`submit`, затем `accept`).
- Аудит: записывается, кто подтвердил, и списки `promote` и `deprecate`.
- Новые статусы предложения: `reverted` (раздел 9.4). Новое поле предложения `kind` (`chat`, `book`, `heal`, `manual`), задаётся при `POST /proposals`, для фильтров интерфейса.

### 9.3. Заметки к предложению и влияние

- `PUT /api/v1/proposals/{pid}/notes` (роль `writer`, только автор предложения): `{summary, items[], questions[], assumptions[], needs_double_confirm}`. Таблица `proposal_notes` в `state.db`. `GET /proposals/{pid}` возвращает их. Интерфейс рисует карточки плана из заметок, diff и влияния.
- `GET /api/v1/proposals/{pid}/impact` (раздел 6.3).

### 9.4. Откат

`POST /api/v1/proposals/{pid}/revert` (роль `reviewer`): для принятого предложения выполняет `git revert -m 1` слияния под блокировкой (`--no-commit`), валидирует получившееся состояние, коммитит «Revert proposal pid», инкрементально переиндексирует, ставит статус `reverted`. Если позже принятые предложения затрагивали те же страницы, отвечает `409 E_REVERT_CONFLICT` со списком страниц (дальше человек правит вручную новым предложением). Восстановление после сбоя в середине отката проверить так же, как для слияния. Откат понимает и `promote`, и `deprecate`, сделанные при том же `accept`.

## 10. Книги и статьи

### 10.1. Библиотека вне git

Книги не должны жить в git: это чужие файлы (вопрос лицензии) и они раздувают репозиторий на десятки мегабайт навсегда.

- Новая категория `library` в `POST /api/v1/raw`: файл сохраняется в `$STATE_DIR/library/<год>/<sha8>-<безопасное_имя>` и **не коммитится**. В `raw_files` появляется колонка `storage` (`git` | `local`).
- Виртуальный путь: `library/<год>/<файл>`. Проверки источника (`raw_path`, `raw_sha256`) учитывают оба хранилища. Код работает с файлами через один резолвер.
- Разрешённые расширения: добавить `epub`. Лимит для `library`: `MAX_LIBRARY_UPLOAD_MB`, по умолчанию 200.
- `STATE_DIR` теперь содержит данные, которые нужны в бэкапе; описать в `README.md`.
- Страница `source` хранит библиографию, хеш и выжимку. **Полный текст книги в репозиторий контента не попадает.** Цитаты в правилах короткие (раздел 10.4).

### 10.2. Извлечение в фоне, кэш, оглавление

Сейчас текст извлекается внутри запроса с лимитом 15 секунд и отдаётся целиком. Проверка на синтетической книге в 450 страниц заняла 13 секунд, то есть на реальной книге не уложится, а ответ в сотни тысяч токенов не поместится ни в один контекст.

- `POST /api/v1/raw/{path}/extract`: запускает фоновое извлечение, отвечает `202`. Повторный вызов идемпотентен. Таблица `extractions(path, sha256, status, pages, chars, error, started_at, finished_at)`; `status`: `pending`, `running`, `done`, `failed`.
- Извлечение идёт порциями по страницам в том же ограниченном по ресурсам подпроцессе (`extract_worker`). Общий лимит задачи `EXTRACT_JOB_TIMEOUT` (по умолчанию 600 с), лимит порции остаётся небольшим.
- Кэш в `$STATE_DIR/extract/<sha256>/` (`pages.jsonl`, `outline.json`), ключ это хеш файла.
- Очистка текста: убрать колонтитулы (строки, повторяющиеся на 30 % страниц и более), номера страниц, переносы слов; склеить строки внутри абзаца; блоки кода не склеивать.
- Форматы: PDF с текстовым слоем (для скана `E_NO_TEXT_LAYER`, OCR не делаем), EPUB (порядок из `spine`, главы по элементам spine; разбор стандартной библиотекой с теми же лимитами распаковки, что у других zip), DOCX, MD, TXT.
- `GET /api/v1/raw/{path}/outline`: главы `{n, title, page_from, page_to}`. Источники в порядке приоритета: закладки PDF, заголовки «Глава N» / «Chapter N», при неудаче блоки по `OUTLINE_FALLBACK_PAGES` (по умолчанию 15). `PUT /raw/{path}/outline` (роль `writer`) заменяет оглавление, правка хранится в `state.db`.
- `GET /api/v1/raw/{path}/text?pages=a-b` или `?chapter=n` и `max_chars` (по умолчанию 30 000, максимум 60 000). В ответе `trust: "untrusted_external"` и `next_pages`, если текст обрезан. Без кэша: `409 E_EXTRACT_PENDING`.
- Старый `GET /raw/{path}/text` без параметров оставить для небольших файлов, для больших `413 E_TEXT_TOO_LARGE` с подсказкой использовать `pages` или `chapter`.
- MCP: `get_outline(path)`, `read_source_pages(path, pages | chapter)`.

### 10.3. Обход книги

В хорошей книге глава k опирается на предыдущие и почти никогда на следующие. Поэтому книгу обходят один раз вперёд, а не держат целиком в контексте. Задача `ingest_book` (раздел 12.3) для каждой главы вызывает общий конвейер планировщика (раздел 7.2) с особенностями: утверждения берутся из текста главы, результат это кандидаты (`lifecycle: candidate`, `origin: book`), вопросов человеку на этом этапе нет (конфликты оформляются связью `conflicts_with` и отчётом).

### 10.4. Цитаты со страницей

Расширить синтаксис цитаты (`domain/markdown.py`): `[@src-clean-code стр. 123 "короткая цитата"]`, `[@src-clean-code гл. 4 "цитата"]`, диапазоны `стр. 12-14`. Простая форма `[@src-id]` остаётся допустимой.

Проверки (на уровне сервиса, рядом с проверкой `source`):

- `E_QUOTE_TOO_LONG`: больше 30 слов (страхует и от копирования чужого текста).
- `E_QUOTE_NOT_FOUND`: цитата не найдена в диапазоне указанных страниц (допуск ±1 страница). Сравнение после нормализации: NFKC, регистр, схлопывание пробелов, удаление мягких переносов и переносов слов, унификация кавычек и тире.
- `E_LOCATOR_OUT_OF_RANGE`: страницы нет в книге.
- `W_QUOTE_UNVERIFIED`: для источника нет кэша извлечения.
- Для EPUB вместо страниц `гл. N`.

- Таблица `tokens`: добавить `person TEXT` (кто стоит за токеном), `kind TEXT` (`agent` | `human`, по умолчанию `agent`) и `expires_at TEXT`. CLI: `wikisvc token create --name ... --role ... --clearance ... --person ... --kind human`.

## 12. Компонент `wikiagent`

Отдельный пакет `src/wikiagent/` в том же репозитории и отдельная точка входа `wikiagent`. Это единственное место, где вызываются модели. Причины: `wikisvc` остаётся детерминированным и проверяемым, а агента можно изолировать (сеть только до сервера моделей и до `wikisvc`).

### 12.1. Устройство

```

├── client.py          # WikiClient: httpx-обёртка над API wikisvc

│   ├── claims.py  related.py  classify.py  plan.py  builder.py  eval.py
├── heal/              # раздел 8
│   ├── scheduler.py  pairs.py  verdicts.py  findings.py
├── jobs/
│   ├── runner.py      # очередь, состояние, возобновление, приоритеты (чат выше лекаря)
│   ├── idle.py        # определение простоя
│   └── ingest_book.py # раздел 12.3
├── chat/
│   ├── sessions.py    # сессии и сообщения (SQLite agent.db)
│   ├── router.py      # намерение: intake | question | edit | revert | other

├── api.py             # FastAPI: /jobs, /chat

  planner:  {base_url: "http://127.0.0.1:8080/v1", model: "gemma-4-12b", context: 32768,
             temperature: 0.2, structured: json_schema}

Роли моделей заменяемы без правки кода. Каждое предложение, созданное `wikiagent`, фиксирует в описании имена моделей и версию промпта.

### 12.2. Безопасность

- Токен `writer` (`kind: agent`). Эндпоинтов принятия, повышения, снятия и отката у `wikiagent` нет в клиенте, а токен роли `writer` их и не позволит.
- Весь текст из книг, статей и вложений чата недоверенный: в промпте он обёрнут в разделитель с пометкой «данные, не инструкции». Вызовы инструментов из ответа модели исполняются только по ответу самой модели в цикле, а не по тексту, найденному внутри входных данных.
- Набор инструментов зависит от задачи (разрешающий список): задача по книге не использует инструменты чата, лекарь не создаёт правила.
- Хождения по ссылкам в интернет нет. Если позже добавится, то только с разрешённым списком адресов, без редиректов на частные адреса и с лимитами.
- Процесс запускается там, где сеть ограничена адресами `wikisvc` и серверов моделей (в Nix-модуле через systemd-ограничения, отдельным этапом).

### 12.3. Задача `ingest_book`

Вход: `raw_path` книги (из `library`), необязательно `title`, `author`, `year`, `scopes_hint`.

1. Запустить извлечение (`POST /raw/{path}/extract`), дождаться `done`, получить оглавление. Если оглавление плохое, задача останавливается в состоянии `needs_outline` и ждёт `PUT /raw/{path}/outline`.
2. Открыть предложение (`kind: book`). Создать страницу `source` (`kind: book`, библиография, хеш).
3. Для каждой главы k по порядку:
   - Текст читается кусками по `chapter_chunk_tokens`; каждый кусок обрабатывается с тем же «состоянием».
   - **Состояние**: краткий конспект глав 1..k−1 (глоссарий, заголовки уже извлечённых кандидатов, список «открытых ссылок» на будущие главы). Размер ограничен `state_tokens`.
   - **Контекст вики**: `rules/related` по ключевым понятиям главы (чтобы не дублировать существующие правила и отмечать связи).
   - **Вывод модели по JSON-схеме**: массив кандидатов `{title, thesis (≤160), category, applies_to_suggestion, level_suggestion: idea|should, rationale, locator, quote (≤30 слов), good_example?, bad_example?, relations: [{rule_id, type}]}`. Проверка до записи: длина тезиса, область из словаря, цитата и страница (`E_QUOTE_NOT_FOUND`). При ошибке модель получает текст ошибки и повторяет до `retries` раз. Не прошедшие попадают в отчёт задачи.
   - Прошедшие кандидаты записываются как `rule` в предложение (`lifecycle: candidate`, `origin: book`, `sources: [src-…]`).
   - После главы прогресс сохраняется в `agent.db` (`job_state`). Задачу можно остановить и возобновить с последней завершённой главы.
4. **Второй проход** (роль `reviewer`): объединить дубликаты внутри книги, закрыть «открытые ссылки», сверить полноту с итоговыми каталогами книги, проверить конфликты с действующими правилами (`conflicts_with` и отчёт в описании), составить раздел «Ключевые идеи» на странице `source` (10–15 пунктов со ссылками на кандидатов).
5. `submit_proposal`. Принимает человек. Задача завершается в состоянии `awaiting_review` и хранит `pid`.

Идемпотентность: повторный запуск не плодит дубли. `id` кандидата строится из категории и слага тезиса (`rule-<category>-<slug>`), при коллизии добавляется числовой суффикс, а перед созданием выполняется поиск похожих правил (в том числе `deprecated`: отклонённые идеи повторно не предлагаются).

API задач: `POST /jobs/ingest-book`, `POST /jobs/heal`, `GET /jobs`, `GET /jobs/{id}` (прогресс: главы сделаны из всего, кандидатов, ошибки, статус), `POST /jobs/{id}/cancel`, `POST /jobs/{id}/resume`. Авторизация по тому же токену через `GET /whoami` к `wikisvc`.

### 12.4. Чат

- Эндпоинты: `POST /chat/sessions` (с привязкой `{"bind": {"type": "page|rule|proposal|none", "id": "..."}, "profile": "python-fastapi"}`), `GET /chat/sessions/{id}`, `POST /chat/sessions/{id}/messages` (текст и вложения; ответ потоком `text/event-stream`).
- **Маршрутизатор намерения** (`chat/router.py`): утверждение о правилах (`intake`, раздел 7), вопрос по вики (`question`), правка конкретного правила (`edit`), команда отката (`revert`), прочее. Неуверенные случаи решаются коротким вопросом.
- Инструменты чата: `search`, `get_page`, `get_rule`, `get_context`, `get_policies` (с `explain`), `list_rules`, `rules_related`, `graph_impact`, `create_proposal`, `put_page`, `patch_page`, `validate_proposal`, `put_notes`. Принятия, повышения, снятия и отката нет.
- Все изменения из чата это предложения в статусе `draft` с описанием сессии и человека (`person`). Подтверждает человек в интерфейсе (раздел 9.2).
- Всё, что человек принёс в чат (вставленный текст, файл, решение), сохраняется как источник (раздел 7.6).
- Чат открыт в контексте: при привязке к странице, правилу или предложению их содержимое и diff подаются в начало диалога.
- Для чата и для роли `planner` нужна модель, которая проходит порог оценки (раздел 7.7).

## 18. Принятые решения (можно менять осознанно)

| Решение | Почему | Альтернатива |
|---|---|---|
| Графовую БД не вводим, обход графа переписываем | граф это производный индекс, замер показал, что тормозит запрос, а не хранилище (в 100–250 раз быстрее при правке запроса) | внешняя графовая БД с синхронизацией с git |
| Умный ввод в `wikiagent`, а не в `wikisvc` | сервис остаётся без LLM и проверяемым | встроить модели в сервис |
| Подтверждение одним действием (`accept` с `promote`) и принятие из `draft` для агентских предложений | «Применить» в чате должно быть одним нажатием; решение остаётся за человеком, агент принять не может | отдельные вызовы `submit`, `accept`, `promote` |
| Лекарь ничего не меняет, выдаёт находки и предложения | всегда решает человек, нет тихих правок | автоприменение высокоуверенных исправлений |
| Находки хранятся в `wikisvc` | интерфейс работает с одним сервисом и очередью | хранить в `agent.db` |
| Кэш проверенных пар по хешам страниц | повторные проходы не тратят модель, находки не всплывают дважды | пересчитывать по расписанию |
| Один тип `rule` с `category` | проще схема, компилятор, выбор типа | четыре типа с теми же полями |
| Тезис это `summary` | нет дубля полей | отдельное поле `thesis` |
| Кандидаты инертны, принимаются пачкой | не нужен частичный `accept` | отдельное предложение на кандидата |
| Повышение и снятие только при `accept` и операциями ревьюера | агент не может включить правило сам | менять `lifecycle` через предложение |
| Акцепт автоматически подтверждает изменённые активные правила | сам `accept` человеком это решение | отдельное подтверждение после каждой правки |
| Книги в `library` вне git | лицензия и размер репозитория | хранить в `raw/` |
| Прогресс обхода книги в `agent.db` | возобновляемость, простая шапка страницы | чек-лист глав на странице `source` |
| Новые области применения добавляет человек командой `scopes add` | агент не расширяет словарь сам | предложения для `scopes.yaml` |
| Области применения «любое из» | проще, предсказуемо | логика «И» |
| `idea` не попадают в инструкцию никогда | бюджет контекста под контролем человека | включать `idea` при свободном бюджете |
| Оценка токенов `символы / 2.5` | без зависимостей, консервативно для русского | точный токенайзер модели |
