# ADR-0001 — Git-репозиторий для контента и SQLite для состояния
status: accepted | date: 2026-09-30

## Контекст

Вика — знания для ИИ-агентов, которые правят люди и агенты. Нужны история, diff, ревью и откат правок,
а также хранилище токенов, предложений и поискового индекса. Команда маленькая, сервер один.

## Решение

Источник правды — markdown-файлы в git-репозитории (RES-wiki-repo); предложение — ветка `proposal/<pid>`
и git worktree в `$STATE_DIR/worktrees/`. Состояние сервиса — SQLite `state.db` (RES-state-db),
индекс — отдельный SQLite `wiki.db` (RES-index-db), который пересобирается из файлов.

## Почему

- ветки, diff, слияние и история — из коробки git, `git log` показывает автора каждой правки;
- ноль инфраструктуры: нет сервера БД, бэкап — архив каталогов;
- индекс производный, его можно удалить и собрать заново (`wikisvc reindex --full`);
- объёма SQLite хватает на тысячи страниц (`ref/wiki-service-spec-v1.md`, раздел 18).

## Что рассматривали и отвергли

| вариант | почему нет |
|---|---|
| PostgreSQL (+ pgvector) | лишний сервер для одного узла; оставлен как путь «если вырастем» |
| таблица черновиков в БД вместо worktree | пришлось бы писать свои diff и слияние |
| хранить страницы в БД | теряется история git и ручная правка файлов |

## Последствия

- запись только одним процессом под `write.lock` (ADR-0004);
- расходится с rule-stack-postgres-default: постоянные данные в SQLite (RISK в отчёте infra-агента);
- `STATE_DIR` — данные для бэкапа, а не кэш (там же библиотека, ADR-0008);
- затрагивает: LIB-wikisvc-core, SVC-wikisvc, RES-wiki-repo, RES-state-db, RES-index-db, DEP-nix-git, DEP-nix-sqlite.
