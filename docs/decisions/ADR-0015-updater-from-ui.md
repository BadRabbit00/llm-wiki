# ADR-0015 — Обновление из интерфейса через демон llm-wiki-updater
status: accepted | date: 2026-10-13

## Контекст

Ручное обновление (pull, проверка, копия, смена дайджеста, миграции, старт) долгое и легко ошибиться.
Замена работающего кода должна оставаться решением человека.

## Решение

SVC-updater — Go-демон хост-части от root (ADR-0009). Слушает только сокет systemd
`/run/llm-wiki-updater/api.sock` (`root:llm-ui 0660`); к нему ходит только wiki-ui, проксируя `/updater-api/`
с токеном сессии; каждый запрос демон проверяет у wikisvc через `/whoami` и пускает только человека с ROLE-admin.
Предлагается только образ, для которого `cosign verify-attestation` подтвердил `release.yml` этого
репозитория для этого тега. Подтвердить можно только предложенный демоном дайджест.

## Почему

- авторизация остаётся в wikisvc, узость — в интерфейсе сокета;
- `cosign` не требует токена GitHub, в отличие от `gh attestation verify`;
- шаги: pull → verify → задачи до → stop → архив → switch → migrate → start → health → задачи после → prune;
  сбой после переключения восстанавливает архив, текущие данные откладываются в `*.failed-*`
  (rule-deploy-release-rollback);
- агент на SIGTERM ставит задачи на паузу на чекпоинте, `recover()` поднимает их после старта.

## Что рассматривали и отвергли

| вариант | почему нет |
|---|---|
| только ручное обновление | долго, ошибки оператора |
| демон сам продолжает прерванное обновление | неверная догадка о состоянии хуже просьбы к человеку |

## Последствия

- демон работает от root — осознанное отступление от rule-deploy-runtime-hardening (RISK в отчёте infra-агента);
- хранит три последних архива перед обновлениями; проверяется `deploy/vm-update-test.nix`;
- затрагивает: SVC-updater, SVC-wiki-ui, SVC-wikisvc, RES-host, RES-container-image, FLOW-release-update.
