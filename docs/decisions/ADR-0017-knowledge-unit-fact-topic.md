# ADR-0017 — Единица знания: атомарный факт `fact` плюс страница-хаб `topic`
status: accepted | date: 2026-10-20

## Контекст

v3 превращает свод правил в базу знаний обо всём, с которой любая модель работает через один MCP
(ТЗ §1). Нужна единица хранения и доставки: агенту в контекст идёт «тезис с id, подробности — по id»
(ТЗ §7), бюджет `ask` по умолчанию 1 500 токенов (NFR-ask-budget). Одна книга даёт тысячи
утверждений (ТЗ §8.1), а человек должен видеть актуальное состояние темы. Решения о слоях (знания,
правила, практика) и путях `kb/{domain}/{kind}/{slug}.md` — ТЗ §1–2.

## Решение

Гибрид: атомарный факт `fact` (одно проверяемое утверждение, пара `claim`/`summary`) — единица
доставки и дедупликации; страница-хаб `topic` с упорядоченным списком `Facts` и выжимкой `Digest`
собирает факты темы. Рядом — `tech` (технология с `verdict`) и `question` (явное «не знаем»).
Тонкая навигация — хабы и рёбра `part_of`, а не вложенные папки; домен у страницы один.

## Почему

- proposition-level retrieval даёт +9–12 Recall@5 и +5–8 EM при бюджете 100 слов против
  passage-level (Dense X, arXiv:2312.06648; ТЗ §0);
- хаб даёт «актуальное состояние темы», которого не хватает атомарным заметкам (ТЗ §0); порядок
  `Facts` — канонический порядок выдачи, а он меняет ответ модели в 50.8–84.4 % случаев при
  перестановке (Stable-RAG, arXiv:2601.02993; ТЗ §7.1);
- пара «минимальный `claim` / деконтекстуализированный `summary`»: «molecular fact» (arXiv:2406.20079),
  DnDScore (arXiv:2412.13175) — от деконтекстуализации FActScore меняется на 13 пунктов, 19 % вердиктов
  переворачиваются (ТЗ §3.1);
- L0 — дословный `claim`: extractive бьёт abstractive на HotpotQA при 11 % токенов (RECOMP,
  arXiv:2310.04408); `claim` — полное предложение: +15–20 % к нахождению документа (arXiv:2511.13900; ТЗ §7);
- практики Karpathy-вики называют главной болью «границы тем ad hoc» и index.md, который ломается на
  200–500 документах; факт задаёт границу утверждением, хаб — явным списком (ТЗ §2).

## Что рассматривали и отвергли

| вариант | почему нет |
|---|---|
| только страницы-темы (passage-level) | теряется выигрыш proposition-level retrieval (Dense X); дедупликация по целым страницам невозможна |
| только атомарные заметки без хабов | нет «актуального состояния темы» и порядка чтения; границы тем ad hoc (ТЗ §2) |
| глубокое дерево папок для тонкой навигации | перенос файлов ломает пути; хабы и `part_of` перестраиваются без переноса, ID не ломаются (ТЗ §2) |
| `term` для технических определений | `term` остаётся для бизнес-терминов заказчика; определение — `fact` с `kind: definition` (ТЗ §3.5) |

## Последствия

- агент получает факты по id и не пересказывает их (INV-cite-by-id); выдача детерминирована
  (INV-canonical-order); одно утверждение на факт (INV-claim-minimal), один домен на страницу (INV-one-domain-per-page);
- объём ревью растёт до тысяч фактов на книгу — решается маршрутизацией (ADR-0024) и окнами ingest (ADR-0027);
- lint получает проверки хабов (`W_HUB_EMPTY`, `W_HUB_TOO_LARGE`, `W_HUB_FACTS_MISMATCH`) — CLS-wikisvc-core.Lint;
- затрагивает: ENT-fact, ENT-topic, ENT-tech, ENT-question, ENT-domain, TERM-fact, TERM-claim, TERM-topic,
  FMT-wikisvc-core.fact, FMT-wikisvc-core.topic, FMT-wikisvc-core.tech, FMT-wikisvc-core.question,
  FMT-wikisvc-core.domains, DTO-wikisvc-core.FactView, TBL-wikisvc-core.index.facts_fts, CLS-wikisvc-core.Knowledge,
  API-wikisvc.knowledge.fact, API-wikisvc.knowledge.topic, API-wikisvc-mcp.get_fact, API-wikisvc-mcp.get_topic.
