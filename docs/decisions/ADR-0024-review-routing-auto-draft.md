# ADR-0024 — Трёхуровневая маршрутизация ревью: авто-блок принимает человек одним действием
status: accepted | date: 2026-10-20

## Контекст

«The Rust Programming Language» даёт 8 000–12 000 сырых фактов (ТЗ §8.1). Стоимость извлечения не
фактор, фактор — ревью. Сейчас любое изменение — предложение, принимает только человек
(INV-human-decides; `AGENTS.md`, граница 1: ни один автоматический путь не получает `accept`).
ТЗ §8.6 предлагало принимать класс «авто» в `draft` без ревью.

## Решение

Предложение — на хаб, ≤ 60 фактов (CFG-wikiagent.ingest.proposal_max_facts). Каждый факт получает класс
ревью и список причин (STATE-fact-review-class, FLOW-fact-review-routing):

| класс | условие | что происходит |
|---|---|---|
| авто | `confidence: sourced`, цитата проверена, кандидатов в дубликаты нет, `kind ≠ convention` | факты собираются в авто-блок предложения; человек принимает блок одним действием без построчного ревью |
| очередь | `inferred`, есть `refines`, `W_POSSIBLE_DUPLICATE`, `kind: convention`, `novelty: unique` | обычное ревью списком L0 |
| пара | `contradicts` | обязательное ревью пары: оставить оба / `replaces` / снять |

Класс «авто» — только сортировка и группировка (INV-auto-class-scope). Системного пути приёма нет: ни
`decided_by = auto`, ни флага автоприёма; INV-human-decides и граница 1 `AGENTS.md` не меняются; `revert` —
обычный (решение Q-kb-auto-accept-human-decides, вариант 1). Человек отдельно решает всё, что меняет смысл:
повышение в `verified`, конфликты, нормативные утверждения, `replaces`. Выборочная проверка split/merge —
~50 фактов на главу.

## Почему

- без группировки 10 000 фактов ревью не переживёт; времени ревью в литературе нет ни у кого, единственный
  ориентир — «один источник трогает 10–15 страниц» у Karpathy (ТЗ §8.6);
- трёхуровневая схема — по MemGuard/Mem0 (ТЗ §8.6);
- брак хороших экстракторов 0.7–1.3 % неверных и 3–5 % не самодостаточных единиц: первое снимает проверка
  цитаты сервисом, второе ловит только человек — поэтому «авто» только для `sourced` с проверенной цитатой (ТЗ §8.3);
- `unique` — самые ценные и самые вероятно неверно извлечённые — в очередь (ТЗ §8.5);
- аннотаторы FActScore разделяли 18 % и сливали 34 % LLM-фактов — отсюда выборка split/merge (ТЗ §8.6);
- приём человеком одним действием сохраняет инвариант при почти той же стоимости ревью.

## Что рассматривали и отвергли

| вариант | почему нет |
|---|---|
| ручное построчное ревью всех фактов | не переживёт тысячи фактов на книгу (ТЗ §8.6) |
| системный авто-приём в `draft` (ТЗ §8.6) | нарушает границу 1 `AGENTS.md` и INV-human-decides (Q-kb-auto-accept-human-decides) |
| авто-приём сразу в `verified` | меняет смысл — нарушает INV-human-decides |
| предложение на главу | хабы — по понятиям, не по главам (ТЗ §8.4); глава даёт 500–700 фактов |

## Последствия

- человек принимает авто-блок, не читая каждый факт: часть не самодостаточных фактов попадёт в `draft` —
  RISK-kb-auto-accept-quality; компенсаторы — `revert`, выборка split/merge, `verified` только руками;
- область класса «авто» сужена инвариантом INV-auto-class-scope;
- UI показывает авто-блок отдельно и причины по каждому факту очереди;
- приёмка этапа 3: «авто» ≥ 70 %, цитаты ≥ 90 % (NFR-ingest-quality);
- затрагивает: INV-human-decides, INV-auto-class-scope, STATE-fact-review-class, FLOW-fact-review-routing,
  FLOW-fact-ingest, JOB-wikiagent.ingest-book, CFG-wikiagent.ingest.proposal_max_facts, NFR-ingest-quality,
  API-wikisvc-mcp.propose_fact, ADR-0022, ADR-0026.
