# Решения реализации

1. Код находится в корне этого репозитория, контент — в соседнем `wiki/`.
   Имя каталога кода произвольное. Dev shell задаёт `WIKI_ROOT=../wiki`;
   состояние и индекс лежат в `.dev/` корня кода, вне контента.
2. Текущий объём — M1–M8 policy-layer-spec.md. Первоначальные этапы 0–7
   сохранены; заготовка эмбеддингов удалена. После M8 добавлен отдельный UI
   в `ui/` (Go + React/TypeScript). OCR, OIDC и NixOS-модуль
   wikiagent остаются за рамками v2. Аудит и лимит запросов на токен реализованы.
3. Все Python-зависимости, включая `mcp` и `pystemmer`, проверены через `nix eval`
   в `python312Packages`; установка через pip не требуется.
4. Flake использует `genAttrs` вместо дополнительной зависимости flake-utils.
5. Канонический словарь связей (§4.5) имеет приоритет над примерами, где
   встречаются обратные `automated_by`, `has_participant` и отсутствующая `uses`.
   Обратные связи вычисляются, записывать их нельзя. Для чтения/записи данных
   используются `reads`/`writes`, для общей зависимости — `depends_on`.
6. Корень контекста возвращается целиком даже при бюджете меньше его размера
   (§7.5.1). Бюджет ограничивает соседей; ответ честно показывает фактическую
   длину. Сосед, не поместившийся ни одним разделом, входит в `omitted_ids`.
7. `raw` не имеет поля sensitivity в спецификации. Все исходники доступны
   с допуском `restricted`; метаданные и pending тоже. Это предотвращает
   чтение закрытого содержимого через исходник публичной страницы.
8. `app-doc` сохраняет полный slug после `appdoc-` (как определено §4.3),
   включая slug родительского приложения. `index` зарезервирован для app.
9. Короткий summary — ошибка схемы; `W_SUMMARY_WEAK` дополнительно доступен
   в мягком lint для файлов, изменённых вне сервиса. При submit ошибки
   ограничены изменёнными страницами и новыми проблемами наложения: чужой
   старый сломанный файл не должен блокировать независимое исправление.
10. Сроки хранятся как UTC ISO-8601 timestamps, а YAML-даты также принимаются.
    Точность времени нужна для `W_STALE_DEPENDENCY` при правках в один день.
11. Proposal виден только если клиент имеет доступ ко всем изменённым
    страницам, включая их предыдущие версии. Частичный diff может скрыть
    важную часть изменения, поэтому такое предложение возвращает 404.
12. Только автор или reviewer/admin может менять чужое предложение.
    Перед accept повторно проверяются версия main и всё наложение; конфликт
    слияния отменяется, main остаётся чистым, предложение сохраняется.
13. MCP SDK закреплён `>=1.29,<2`, соответствуя nixpkgs в flake.lock.
    Используем официальный FastMCP v1 и stdio; HTTP-транспорт необязателен.
    [Документация SDK v1](https://py.sdk.modelcontextprotocol.io/v1/).
14. nixpkgs `7a0f122` + Python 3.12: у `inline-snapshot 0.34.2` падают три
    snapshot-теста `tests/test_docs.py` (расходятся номера строк примеров).
    Flake исключает только этот файл тестов транзитивной build-зависимости;
    остальные тесты зависимостей и все проверки wikisvc остаются включены.
15. Полный reindex очищает производные таблицы и пересобирает их одной
    SQLite-транзакцией вместо удаления открытого WAL-файла. Читатели видят
    целостный снимок; статистика выдачи сохраняется. Индекс остаётся полностью
    удаляемым при остановленном сервисе. Без `--full` используются изменения Git.
16. Бюджет контекста считает `body_md`, без JSON и полей метаданных.
    Разделы H2/H3 неделимы при выдаче контекста; длинный абзац при поисковой
    индексации режется на части до 1500 символов, если границы абзацев не хватает.
17. Загрузка immutable raw — отдельный разрешённый коммит (§8.6), исключение
    из правила предложений для страниц. `note` хранится в state.db, не в raw.
18. Proposal наследует минимальный допуск автора при создании, а его diff
    дополнительно проверяет чувствительность всех старых и новых страниц.
    Аудит доступен только admin с restricted, поскольку содержит закрытые ID.
19. TTL проверяется при старте и создании нового предложения. Без фонового
    потока нет дополнительного процесса записи. Diff закрытого предложения
    хранится в state.db; после удаления worktree он остаётся доступен ревьюеру.
20. YAML-алиасы в frontmatter и схеме запрещены для защиты от рекурсивных
    структур. Значения задаются явно. Эта вики не требует YAML anchors.
21. Все редактирования сбрасывают страницу в draft, включая правки ревьюера.
    Подтверждение всегда выполняется явной операцией verify; verified_* клиент
    назначить не может. verify не меняет updated (дата фактического содержания).
22. Номер ADR — подсказка следующего свободного номера с учётом открытых
    предложений, а не бронирование. Конкурирующие создания проверяются на submit/accept.
23. Лимит запросов — фиксированная календарная минута в state.db, общий для
    HTTP и MCP одного токена. По умолчанию выключен. Запрос health не учитывается.
24. Записи ограничены путями операции. Служебный журнал в Git directory
    позволяет откатить незакоммиченные файлы после исключения и перезапуска,
    не затрагивая inbox, Obsidian и локальные заметки. Генераторы выполняются
    до финального merge-коммита; принятый коммит не откатывается из-за сбоя индекса.
25. `last_editor` дополняется множеством всех редакторов: иначе очередная правка
    автора позволила бы предыдущему редактору принять собственное изменение.
    При обновлении старой базы редакторы восстанавливаются из истории worktree.
26. Точные шаблоны секретов проверяют исходный текст. Обычные хеши длиной
    32/40/64 hex-символа исключены только из энтропийной эвристики; пароль или
    Bearer с таким значением по-прежнему блокируется. Разрешены явные шаблоны
    `${VAR}`, `<секрет>`, `<password>`; произвольные угловые скобки не скрывают ключи.
27. Инкрементальный индекс читает только изменённые Markdown, остальные страницы
    берёт из SQLite. Локальные проверки кэшируются по содержимому и схеме,
    межстраничные ограничения проверяются на всём актуальном наложении.
    Full reindex остаётся способом восстановления индекса. Сырьё повторно
    хешируется при изменении пути, размера или mtime; ручное изменение raw запрещено.
28. Поле `score` удалено из выдачи HTTP/MCP как намеренное изменение примера §7:
    числовой BM25 раскрывал статистику скрытых страниц. Ранжирование сохранено;
    полностью устранить влияние скрытого корпуса на порядок это не обещает.
29. PDF/DOCX разбираются отдельным процессом с лимитами памяти, CPU, времени и
    длины текста. Библиотеки документов входят в Nix dev/check, оставаясь
    необязательными зависимостями установленного сервиса.
30. После ревью шаблон получил пять стартовых тегов вместо пустого списка (§11).
    Неизвестные теги по-прежнему запрещены; существующие словари не перезаписываются.
    Генерируемый индекс сгруппирован по типам, журнал содержит `[accept]` и автора.

## Policy layer v2

1. M1: обязательное правило требует владельца и sources с решением (§1); для
   владельца допустим ID человека, а `role-*` проверяется как ссылка на роль.
2. Новое правило через обычный PUT всегда получает candidate/should/priority=3.
   Миграция старых типов создаёт candidate/idea, как отдельно предписано §3.6.
   Правка существующего правила сохраняет все защищённые поля и предыдущую
   атрибуцию подтверждения; публикацию правки подтверждает accept.
3. `schema upgrade` — явная административная операция с журналом Git: добавляет
   недостающие файлы схемы, обновляет source/связи и удаляет четыре старых типа.
   Содержимое страниц меняет только `migrate-rules` через draft-предложение.
   Перед миграцией применяют schema upgrade; dry-run ничего не записывает.
4. M2: бюджет включает весь экспортируемый Markdown. `enforced=all` включает
   машинно проверяемые правила, `none` исключает их, `keep_must` сохраняет must.
   Version зависит от включённых страниц, параметров инструкции и её шаблона;
   explain и счётчики использования версию не меняют. Кэш разделён по допуску
   и сбрасывается по поколению индекса даже при reindex без нового Git-коммита.

### Граф и поиск v2

GraphStore внедряется в сервисы чтения, контекста и поиска; SQLite остаётся
единственным адаптером. Impact обходит входящие канонические связи, исключая
автоматические inverse (кроме симметричного conflicts_with). Поиск не раскрывает
сырой BM25 score; related возвращает только порядковый score_rank. Синонимы для
async/sync/requests задают группу темы для отбора потенциальных противоречий,
а не утверждают взаимозаменяемость этих технологий.

### Решения и откат v2

Имя автора токена и его person/kind сохраняются в момент создания предложения;
личность каждого редактора также сохраняется, поэтому смена или отзыв токена не
обходят запрет саморевью. Принимать, подтверждать и снимать могут только human.
Прямое promote существующего кандидата разрешено §9.1; ограничение «в самом
предложении» относится к спискам promote/deprecate внутри accept (§9.2).

Accept выполняет единственный merge commit с решением человека. При ошибке,
включая конфликт слияния, статус предложения сохраняется. Восстановление сначала
возвращает принадлежащие операции пути по журналу, затем abort: изменённые после
слияния защищённые поля иначе мешают Git выполнить abort. Revert проверяет все
последующие коммиты содержательных страниц, сохраняет текущий журнал и заново
генерирует индекс; успешный Git-коммит является точкой фиксации, state.db при
аварии после него восстанавливается по сообщению коммита.

### Изоляция wikiagent и чат

WikiClient допускает фиксированные HTTP-маршруты и никогда не предоставляет
операции принятия/повышения/снятия/отката. Команда отката в чате возвращает
human_action интерфейсу: это согласует §7.2 с прямым запретом агенту в §12.2.
Человеческие токены не сохраняются в agent.db. Допуск вызывающего должен быть
не ниже допуска постоянного токена агента, иначе данные его корпуса могут стать
видны пользователю. Для источников чата/книг рабочий токен требует restricted,
как и существующий API raw. Сессия дополнительно ограничена person владельца.

Переписка сохраняется неизменяемыми ревизиями raw/transcripts, исходная source
обновляется в том же черновике. Длинный ввод делится на планы до 10 пунктов.
Сигнал must остаётся предложением в notes/accept_body; записанный агентом кандидат
инертен и повышается только человеком. Фактические ошибки валидации направляются
модели для ограниченного исправления, выдуманные цитаты отклоняются после 3 попыток.

### Библиотека и прогресс извлечения

POST extract возвращает состояние задачи немедленно. Пакеты извлечения
сохраняются атомарно по хешу источника, поэтому повторный запуск продолжает
существующий кэш. Failed сохраняет код ошибки при повторном POST; произвольный
недоверенный документ не перезапускает парсер бесконечно. Маленькие legacy raw
сохраняют прежнее чтение; library и запросы страниц требуют готового кэша.
Продолжение длинной страницы использует next_pages вместе с next_offset, чтобы
повторный запрос не зацикливался. Для цитаты по странице допустим соседний лист;
для ссылки на главу EPUB проверяется сама глава.

Book checkpoints фиксируют результат модели до записи кандидатов. ID кандидата
зависит от задачи и тезиса, запись до аварии безопасно повторяется. Незавершённые
задачи восстанавливаются при старте, после потерянного ответа submit узнаётся
статус существующего предложения. Уровень кандидатов по умолчанию should согласно
защите новых rule; level_suggestion=idea хранится в ответах модели, но не обходит
защищённое поле. Публикация кандидатов и их повышение остаются отдельными решениями
человека. STATE_DIR содержит библиотеку, кэш, токены и историю — это данные для
резервного копирования, а не только расходный индекс.

### Самолечение

Автоматический запуск требует простоя и попадания в окно по местному времени
сервера. Пустой windows разрешает весь день; окно через полночь поддерживается.
Ручной запуск обходит расписание. Одновременно выполняется одна задача heal,
поэтому суточный бюджет не расходуется конкурентными проходами. Бюджет считает
только heal-вызовы, включая повторы и второе мнение; чат и книги не учитываются.
Перед парой резервируется максимальное число повторов. Неисчерпанный успешный
проход сохраняет хеши; частичный продолжает через кэш пар. Чат получает следующий
вызов модели, текущий HTTP-вызов не прерывается.

Лекарь читает счётчики из доступного writer списка rules, не получает reviewer
ради rules/stats. Детерминированные проверки времени и счётчиков выполняются
даже при неизменных хешах. Дедупликация findings сохраняет dismiss; существующие
находки не расходуют бюджет новых. Автоматические задачи видны reviewer/admin
с достаточным допуском, персональные задачи ограничены владельцем.

### Проверка на локальной Gemma и сборка v2

GGUF из ~/.eva/models проверяется через локальный llama-server без reasoning,
три роли используют один и тот же endpoint. JSON-схема передаётся и как ограничение
декодирования, и как текст с default-значениями: локальный сервер не обязан сам
объяснять схему модели. Defaults и различие конфликта/подтверждённой замены явно
описаны в промпте. Eval получает полноценные фразы и предыдущий план, а не названия
тестов. Ошибки модели отмечаются отдельно; прогон продолжается, отчёт сохраняется
после каждого случая. Порог готовности не снижается под выбранную модель.

Readable ID книги: rule-<category>-<транслитерированный тезис>; коллизия получает
числовой суффикс. Выделенный ID сохраняется в checkpoint до записи; старые jobs
с ID на основе хеша продолжаются по уже существующему кандидату. Ответ только с
удалением кандидата обновляет источник, validation и notes того же предложения;
решения предыдущих шагов сохраняются, отменённое повышение удаляется.

Nix-выводы wikisvc/wikiagent указывают на один wheel с обоими CLI. Это сохраняет
общие контракты и детерминированные типы без зависимости wikisvc от вызовов LLM.
PDF/DOCX входят в runtime. Покрытие расширено: domain/index, компилятор policies
и весь planner. Обновление AGENTS/workflows существующей вики требует явного
флага schema upgrade --refresh-instructions; обычный upgrade их сохраняет.

На реальном прогоне llama-server отверг вложенные количественные ограничения
JSON Schema (раскрытие грамматики превысило допустимую сложность). В v2.3 декодер
ограничивает форму, типы и перечисления; числовые/размерные пределы остаются в
промпте и неизменной Pydantic-валидации после ответа. Неверный тезис/цитата не
попадает в сервис. Повторный live-прогон книги создал валидных кандидатов.
Для локального контекста 16K пример ограничивает главу 4000 токенами, оставляя
место схеме, связанным правилам, состоянию и ответу.

### Анонимные агенты и человеческий вход через OIDC

API/MCP могут работать без токенов только при явном ANONYMOUS_ACCESS=1.
Принципал всегда agent, максимум writer/internal: может предложить изменение,
но не принять его и не прочитать restricted. Все анонимные обращения имеют одну
identity и общий пул предложений; для них нужны сетевые ограничения и лимит по IP.
Это приемлемо для текущей доверенной сети без материалов restricted. При появлении
таких материалов решение об анонимном доступе пересматривается. Сам wikiagent
по-прежнему требует допуск не ниже рабочего токена; анонимный вызов ему запрещён.
Сверка документации из задачи 07 запускается через человеческую сессию UI;
`wk audit` отложен до отдельного решения о сессиях CLI.

UI использует только Authentik authorization code + PKCE. Go проверяет подпись,
issuer, audience, время и nonce, затем предъявляет отдельный reader/agent/public
токен локальному POST /sessions. Его имя проверяется по строке БД: display_name
не даёт права выпуска. Токен запрещён на остальных API-путях и во всём MCP.
Wikisvc не знает OIDC и не делает сетевых запросов. Браузер получает HttpOnly
cookie с ограниченным по времени токеном wikisvc; новые входы зависят от IdP,
уже выданные сессии — только от локального API. Аварийный human-токен используется
напрямую через API, с тем же person, что и sub владельца в Authentik.

Сессионный tokens.name уникален и остаётся ключом лимита; display_name — безопасное
читаемое имя Principal и git-автора. Person хранит стабильный непрозрачный sub.
Таблица people содержит одну запись на person, обновляется при входе и доступна
через GET /people только с internal. UI разрешает identity в display_name,
при отсутствии записи показывает сохранённое имя автора либо identity.
Verified_by, author_identity и проверки саморевью не меняются. Новые decided_by
содержат actor.identity; исторические строки остаются именами. Для токенов без
person значения совпадают, для старых человеческих могут различаться. Это
различие архивного отображения, не изменение прав или машины состояний.
